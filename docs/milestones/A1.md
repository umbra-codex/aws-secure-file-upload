## Goal

The pipeline needs three S3 buckets:

- **Incoming** holds raw uploads until they're scanned.
- **Approved** holds files that passed every check.
- **Quarantine** holds everything else.

All three must be private and encrypted. Instead of writing the same blocks three times, you'll write one reusable **bucket module** and call it three times. That's how Terraform teams avoid copy-paste, and it follows HashiCorp's [module creation pattern](https://developer.hashicorp.com/terraform/tutorials/recommended-patterns/pattern-module-creation): group the things that are always deployed together, and name everything fully.

Every other portion reads these buckets through your outputs, so this milestone unblocks the rest of the team.

### How to read the blocks

Each block below tells you its **block type**, its **type** where it has one (like `aws_s3_bucket`), and its **name**, the label you choose. Only some block types take labels. These are the first lines of every kind of block in this milestone:

```
resource "aws_s3_bucket" "this" {      # block type, resource type, resource name
data "aws_caller_identity" "current" { # block type, data source type, data source name
variable "bucket_name" {               # block type, variable name
output "bucket_id" {                   # block type, output name
module "incoming" {                    # block type, module name
locals {                               # block type only: no labels at all
```

The **Arguments / Set To** table lists every argument to write inside the block and what its value should be:

- **A value in `code` on its own is literal.** Type it as shown: `true`, `"AES256"`, `["POST"]`.
- **A cell that describes a rule** ("`1` when ... is true, otherwise `0`") is asking you to write an expression, not to type one of the values.
- **A cell that names something** is asking for a reference. The translations are:

| The brief says | You write |
|---|---|
| the `foo` variable | `var.foo` |
| the `bar` local | `local.bar` |
| the `id` (or `arn`, `bucket`, ...) of `aws_s3_bucket.this` | `aws_s3_bucket.this.id` |
| the `account_id` of `data.aws_caller_identity.current` | `data.aws_caller_identity.current.account_id` |
| the `bucket_name` output of `module.incoming` | `module.incoming.bucket_name` |
| X followed by `-incoming` | one string joining both, using interpolation: `"${...}-incoming"` |

**Tags** says what to tag, or that the block doesn't support tags. **Docs** links the reference page.

The names matter: the check looks for these exact types and names.

## Start your branch

Do this before you change any file. It gets the latest `main` (which includes M0's scaffold) and creates your branch from it:

```bash
git checkout main
git pull
git checkout -b a1-buckets
git push -u origin a1-buckets
```

The last command publishes the branch and links it to GitHub, so every later `git push` in this brief knows where to go.

You'll open your pull request as a **draft** at your first checkpoint. (GitHub won't create a PR until the branch has at least one commit that `main` doesn't.) A draft PR says "work in progress, not ready for review." Every push after that updates the same PR, and the check result for each push shows on it, so the team can follow along. Run `git branch --show-current` any time to confirm you're on `a1-buckets`, not `main`.

### Commit messages

Every commit message follows [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/): `<type>(<scope>): <description>`. The scope is your milestone ID in lowercase, and each checkpoint gives you the exact message to use. The types you'll see:

| Type | Use it for | Example |
|---|---|---|
| `feat` | new Terraform or Lambda code | `feat(a1): add bucket module variables` |
| `fix` | correcting something that was wrong | `fix(a1): use the bucket's id in the CORS rule` |
| `docs` | READMEs and other docs only | `docs(a1): add bucket module README` |
| `chore` | bookkeeping, like `milestones.txt` | `chore(a1): add A1 to milestones.txt` |

Your pull request's title starts as your first commit (`gh pr create --fill`), so it follows the same format, and you retitle it to the whole milestone before you mark it ready. If a check sends you back to fix something, commit the fix as `fix(<id>): <what you fixed>`.

### main.tf

#### 5. The bucket

**Block Type:** `resource`

**Resource Name:** `this`

#### 6. Block Public Access

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_public_access_block`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `block_public_acls` | `true` |
| `block_public_policy` | `true` |
| `ignore_public_acls` | `true` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_public_access_block](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_public_access_block)

Why reference the bucket's `id` instead of typing the name: the reference tells Terraform to create the bucket first. A typed name can make `apply` fail on the first run, and the check rejects it.

#### 7. Encryption

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_server_side_encryption_configuration`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `rule` (nested block) | one `rule` block containing the block below |
| `rule` → `apply_server_side_encryption_by_default` (nested block) | one block with `sse_algorithm` = `"AES256"` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_server_side_encryption_configuration](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_server_side_encryption_configuration)

A nested block is a block written inside another block, with no `=`. `AES256` is SSE-S3, encryption with keys S3 manages for you. Don't use `aws:kms`: SSE-KMS adds a charge per request and a key policy to maintain, and this project doesn't need it.

#### 8. Versioning (only when switched on)

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_versioning`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `count` | an expression, not a number: it gives `1` when the `enable_versioning` variable is true and `0` when it's false. Use a conditional expression. |
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `versioning_configuration` (nested block) | one block with `status` = `"Enabled"` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_versioning](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_versioning) · [count](https://developer.hashicorp.com/terraform/language/meta-arguments/count) · [conditional expressions](https://developer.hashicorp.com/terraform/language/expressions/conditionals)

`count = 0` means "don't create this". Only Incoming turns versioning on: later, Lambda 2 copies the exact file version GuardDuty scanned, which only works on a versioned bucket.

#### 9. CORS (only when origins are given)

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_cors_configuration`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `count` | an expression, not a number: it gives `1` when the `cors_allowed_origins` variable has at least one item and `0` when it's empty. Use the `length` function inside a conditional expression. |
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `cors_rule` (nested block) | exactly one block, with the four arguments below |
| `cors_rule` → `allowed_methods` | `["POST"]` |
| `cors_rule` → `allowed_origins` | the `cors_allowed_origins` variable |
| `cors_rule` → `allowed_headers` | `["*"]` |
| `cors_rule` → `max_age_seconds` | `3000` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_cors_configuration](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_cors_configuration) · [length function](https://developer.hashicorp.com/terraform/language/functions/length)

Browsers can only upload straight to S3 if the bucket allows their origin. Put every origin in that one rule; don't create one rule per origin.

## Check it

### How to see your results

There are two levels, and they answer different questions. The command in every checkpoint above is the first one; you run it at each step, in your terminal, with no clicks and no commit.

**On your machine, at every checkpoint.**

```bash
scripts/check-local.sh
```

It runs the same `.github/scripts/check.sh` that CI runs, so it cannot drift into a different check. It keeps that check's working files in `.terraform-check/`, so your own `.terraform/` is left alone. It needs Terraform, not AWS: the tests use a mocked provider. It also runs `tflint` when you have it (CI runs it as its own step), warns when your Terraform or `tflint` version differs from the one CI pins (1.16.6 and 0.64.0), and warns when your working tree has uncommitted changes, because GitHub checks commits and not files.

The dependency gate and `tflint` run before the check itself, so when one of them is red the run is red even if every step passed: the summary then has no `👍 A1 passed.` line, and the `Next:` line names that gate and prints its own message. The same is true of a run that stops early, such as a cancelled one on GitHub: the summary says so instead of counting only the rows it happened to see.

It prints one screen. This is a real run on a branch where only step 1 is built:

```
A1: 1 of 5 steps done
  ✅ formatting, init, validate
  ✅ step 1 (variables)
  ❌ step 2 (resources)      <- next
  ❌ step 3 (outputs)
  ❌ step 4 (readme)
  ❌ step 5 (storage)
  ✅ earlier milestones still pass (M0)

Next: A1 step 2 (resources). Re-read docs/milestones/A1.md, "### main.tf", items 5 to 9.
Nothing is named aws_s3_bucket.this yet. Also missing: aws_s3_bucket_public_access_block.this, aws_s3_bucket_versioning.this, aws_s3_bucket_cors_configuration.this.
Run scripts/check-local.sh --explain for the full output.
```

Read it in that order. The summary says which steps are ✅ and which are ❌, and the first ❌ is marked `<- next`. The line beginning `Next:` names the step and the section of this brief to re-read, with the numbered items in it. The line under that is the check's own message: what it expected and what it found. You do not need anything else to start fixing, and your reviewer is not involved yet.

Then fix the file and run the same command again. No commit, no push, no waiting for GitHub: that is the loop, and it usually takes about 20 seconds a turn once the provider is installed (the first run installs it, so it takes longer).

`--explain` prints every line the check printed, unedited, when you want the whole of a failure:

```bash
scripts/check-local.sh --explain
```

When the summary says `👍 A1 passed.`, the milestone is done on your machine. Commit, push, and go to the next checkpoint, or to the closing step if this was the last one.

**On GitHub, once per milestone, before you mark the pull request ready.** GitHub is the authority. A green run on your machine is a preview of the same check, and the two can disagree in the ways listed below. The push at your last checkpoint already started the check there, and the closing step of this brief tells you to run this once:

```bash
scripts/remote-check.sh
```

It looks for the run your push started, waits for it to appear, follows it, and prints the same summary and the same `Next:` lines, so you read GitHub's answer in the shape you already know. It ends with the run's URL. Nothing is saved on your machine. It needs the GitHub CLI, signed in (`gh auth login`).

The run's page itself, when you want the whole log rather than the summary: open the repo on GitHub, click **Actions**, click the newest run, and scroll to **Summary**. The table lists every step, and **Output of the failed steps** holds everything each ❌ printed.

**Why the two can disagree, and what this script already covers.** Your version of Terraform can differ from CI's 1.16.6. `tflint` is a separate CI step, so it is run separately here. The dependency gate is a separate CI step too, and the spec tests are mocked, so `check-local.sh` runs that gate first. GitHub checks commits, not your working tree. And a clone on Windows can change line endings; the repo's `.gitattributes` pins LF, so every checkout matches the runner.

**To re-check after a fix:** fix the file, run `scripts/check-local.sh` until the step is ✅, then format, commit, and push. The push runs the check on GitHub automatically.

The check runs A1 in five steps, one per file, so you can push after each file and see your progress:

| Step | Checks |
|---|---|
| 1 (variables) | `bucket/variables.tf`: the four inputs and their defaults |
| 2 (resources) | `bucket/main.tf`: the bucket and each of its settings |
| 3 (outputs) | `bucket/outputs.tf`: each output points at the right attribute |
| 4 (readme) | `bucket/README.md`: the sections and every input and output name |
| 5 (storage) | `buckets.tf` and `outputs.tf` in `modules/storage/`: the three module calls, their tags, and the storage outputs. It also checks every bucket name against S3's naming rule (3 to 63 characters; lowercase letters, numbers, dots, and hyphens), so you don't write that rule yourself. |

Steps you haven't reached yet show ❌; that's expected. You're done when every step is ✅ and the summary says `👍 A1 passed.`

Reading a failure:

- **"Resource not found: aws_s3_bucket.this"** or **"There is no managed resource ... in the root module"**: no resource with that exact type and name exists yet. Either you haven't built it or you named it differently, so check the block's type and name above. (The test treats the module it's testing as the "root module", so that wording is expected.)
- **"Module not installed"** or **"Unsupported argument"** in a module call: the module call's name or an input name doesn't match this brief.
- **An error like "Invalid function argument" pointing at a line in `tests/`**: the shape is wrong, not the value. Usually a missing `count`.
- **A row called `formatting (fmt -check)` is ❌ and lists file names**: the spacing or `=` alignment in those files isn't what `terraform fmt` produces. From the repo root run `terraform fmt -recursive`, then commit and push again. This row isn't one of the milestone's steps, but it fails the whole run on its own, so a green step table with a red formatting row still isn't done.
- **A row under `formatting, init, validate` is ❌**, or the step table never appears: the check stops there, because no step can run on a configuration that does not format, init, or validate. The `Next:` line names the gate that failed and prints the check's own message. For formatting it lists the files `terraform fmt` would change; for `init` it is usually the provider download, so check your network or the mirror; for `validate` it names the file and line.
- **Any other failed check** prints what it expected and what it got.

## Done when (in your own AWS account)

Run these from the repo root (the folder with `providers.tf` and `backend.hcl`), never from inside `modules/`. Run `init` again whenever a milestone adds or changes a module call.

```bash
terraform init -backend-config=backend.hcl
terraform apply
aws s3api get-bucket-versioning --bucket "$(terraform output -raw incoming_bucket_name)"
aws s3api get-bucket-versioning --bucket "$(terraform output -raw approved_bucket_name)"
echo "hello" | aws s3 cp - "s3://$(terraform output -raw incoming_bucket_name)/uploads/a1.txt"
aws s3api get-bucket-tagging --bucket "$(terraform output -raw incoming_bucket_name)"

# Incoming is versioned: remove every version and delete marker, or destroy fails
BUCKET=$(terraform output -raw incoming_bucket_name)
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' --output json)"
terraform destroy
```

Expected: Incoming reports `"Status": "Enabled"`, Approved reports no versioning status, the upload succeeds, and the tags include `Name`, `Role`, `Project`, `Owner`, and `ManagedBy`. `destroy` can't delete a bucket that still holds anything, including old versions and delete markers, which is why the block empties Incoming first. (`aws s3 rm --recursive` is not enough on a versioned bucket: it only adds delete markers.)

Add `A1` on its own line in `milestones.txt`, then format, commit, and push:

```bash
terraform fmt -recursive
git add -A && git commit -m "chore(a1): add A1 to milestones.txt" && git push
```

## Mark the pull request ready

One last look at the check on GitHub before you mark it ready. `scripts/remote-check.sh` follows the run your last push started, so it needs no new commit and no push:

```bash
scripts/remote-check.sh
```

GitHub is the authority here: a green run on your machine is a preview, and this run is the check's own answer.

Your draft PR has been collecting every push. When every step is ✅ and the "Done when" output is ready:

1. Paste the "Done when" output into the PR description (`gh pr edit --body-file <file>`, or edit it on GitHub, where the PR template is already filled in).
2. Retitle the PR to the whole milestone. The repo is squash-only, so the PR's title becomes the one commit that lands on `main`, and `gh pr create --fill` named it after your first checkpoint. Each brief ends with the exact title to use; for A1:

   ```bash
   gh pr edit --title "feat(a1): add the bucket module and the three buckets"
   ```

3. Mark it ready for review:

   ```bash
   gh pr ready
   ```

A teammate reviews it. Once it's approved and the **ci** check is green, it merges into `main` and the branch deletes itself.
