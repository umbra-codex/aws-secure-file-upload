## Goal

The pipeline needs three S3 buckets:

- **Incoming** holds raw uploads until they're scanned.
- **Approved** holds files that passed every check.
- **Quarantine** holds everything else.

All three must be private and encrypted. Instead of writing the same blocks three times, you'll write one reusable **bucket module** and call it three times. That's how Terraform teams avoid copy-paste, and it follows HashiCorp's [module creation pattern](https://developer.hashicorp.com/terraform/tutorials/recommended-patterns/pattern-module-creation): group the things that are always deployed together, and name everything fully.

Every other portion reads these buckets through your outputs, so this milestone unblocks the rest of the team.

### How to read the blocks

Each block below tells you its **block type**, its **type** where it has one (like `aws_s3_bucket`), and its **name**, the label you choose. Only some block types take labels. These are the first lines of every kind of block in this milestone:

```
resource "aws_s3_bucket" "this" {      # block type, resource type, resource name
data "aws_caller_identity" "current" { # block type, data source type, data source name
variable "bucket_name" {               # block type, variable name
output "bucket_id" {                   # block type, output name
module "incoming" {                    # block type, module name
locals {                               # block type only: no labels at all
```

The **Arguments / Set To** table lists every argument to write inside the block and what its value should be:

- **A value in `code` on its own is literal.** Type it as shown: `true`, `"AES256"`, `["POST"]`.
- **A cell that describes a rule** ("`1` when ... is true, otherwise `0`") is asking you to write an expression, not to type one of the values.
- **A cell that names something** is asking for a reference. The translations are:

| The brief says | You write |
|---|---|
| the `foo` variable | `var.foo` |
| the `bar` local | `local.bar` |
| the `id` (or `arn`, `bucket`, ...) of `aws_s3_bucket.this` | `aws_s3_bucket.this.id` |
| the `account_id` of `data.aws_caller_identity.current` | `data.aws_caller_identity.current.account_id` |
| the `bucket_name` output of `module.incoming` | `module.incoming.bucket_name` |
| X followed by `-incoming` | one string joining both, using interpolation: `"${...}-incoming"` |

**Tags** says what to tag, or that the block doesn't support tags. **Docs** links the reference page.

The names matter: the check looks for these exact types and names.

### main.tf

#### 5. The bucket

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `bucket_name` variable |
| `tags` | the `tags` variable |

**Tags:** yes, through the `tags` argument above. The module passes along whatever the caller gives it, and the module calls in Part 2 set `Name`, `Role`, and `ManagedBy`. (`Project` and `Owner` are added automatically by the provider's `default_tags` in the repo root's `providers.tf`.)

**Docs:** [aws_s3_bucket](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket)

`this` is the conventional name when a module has only one resource of a type.

#### 6. Block Public Access

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_public_access_block`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `block_public_acls` | `true` |
| `block_public_policy` | `true` |
| `ignore_public_acls` | `true` |
| `restrict_public_buckets` | `true` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_public_access_block](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_public_access_block)

Why reference the bucket's `id` instead of typing the name: the reference tells Terraform to create the bucket first. A typed name can make `apply` fail on the first run, and the check rejects it.

#### 7. Encryption

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_server_side_encryption_configuration`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `rule` (nested block) | one `rule` block containing the block below |
| `rule` → `apply_server_side_encryption_by_default` (nested block) | one block with `sse_algorithm` = `"AES256"` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_server_side_encryption_configuration](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_server_side_encryption_configuration)

A nested block is a block written inside another block, with no `=`. `AES256` is SSE-S3, encryption with keys S3 manages for you. Don't use `aws:kms`: SSE-KMS adds a charge per request and a key policy to maintain, and this project doesn't need it.

#### 8. Versioning (only when switched on)

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_versioning`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `count` | an expression, not a number: it gives `1` when the `enable_versioning` variable is true and `0` when it's false. Use a conditional expression. |
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `versioning_configuration` (nested block) | one block with `status` = `"Enabled"` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_versioning](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_versioning) · [count](https://developer.hashicorp.com/terraform/language/meta-arguments/count) · [conditional expressions](https://developer.hashicorp.com/terraform/language/expressions/conditionals)

`count = 0` means "don't create this". Only Incoming turns versioning on: later, Lambda 2 copies the exact file version GuardDuty scanned, which only works on a versioned bucket.

#### 9. CORS (only when origins are given)

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_cors_configuration`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `count` | an expression, not a number: it gives `1` when the `cors_allowed_origins` variable has at least one item and `0` when it's empty. Use the `length` function inside a conditional expression. |
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `cors_rule` (nested block) | exactly one block, with the four arguments below |
| `cors_rule` → `allowed_methods` | `["POST"]` |
| `cors_rule` → `allowed_origins` | the `cors_allowed_origins` variable |
| `cors_rule` → `allowed_headers` | `["*"]` |
| `cors_rule` → `max_age_seconds` | `3000` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_cors_configuration](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_cors_configuration) · [length function](https://developer.hashicorp.com/terraform/language/functions/length)

Browsers can only upload straight to S3 if the bucket allows their origin. Put every origin in that one rule; don't create one rule per origin.

### README.md

#### 16. Module README

Every module documents itself, so the next person can use it without reading the code. Write `modules/storage/bucket/README.md` with these sections, in this order:

| Section | What goes in it |
|---|---|
| `# bucket` (title) | One sentence on what the module creates. |
| `## Requirements` | A table with one row per version requirement, copied from the module's own `versions.tf` (already in the folder): `terraform >= 1.10.0, < 2.0.0` and `aws ~> 6.69`. |
| `## Usage` | One example module call in a code block, the way the storage module calls it. |
| `## Inputs` | A table with columns **Name, Type, Default, Required, Description**, one row per variable. |
| `## Outputs` | A table with columns **Name, Description**, one row per output. |

The check confirms the file exists, has the Requirements, Inputs, and Outputs sections, and has a table row for every input and every output (a name that only appears in the Usage example doesn't count). A2 and A3 add rows to it.

In real teams these tables are often generated by a tool called [terraform-docs](https://terraform-docs.io). It's optional here; writing them by hand once is how you learn what they mean.

## Check it

### How to see your results

The check never runs on your machine. It runs on GitHub every time you push, and the results are stored there: on the run's page under **Actions**, and on your pull request as the **ci** check. There are two ways to see them.

**After a push (automatic):** open the repo on GitHub, click **Actions**, click the newest run, and scroll to **Summary**. The table lists every step with ✅ or ❌. Click **Output of the failed steps** under it to see what each ❌ expected and what it found.

**From your terminal (re-check without pushing):**

```bash
scripts/remote-check.sh
```

This asks GitHub to run the check again on your branch, waits for it to finish, and prints your progress. When the milestone is complete, it looks like this:

```
Checking the last commit you pushed to a1-buckets (3f2c1ab)
Waiting for GitHub to start the run...
Run finished in 58s

A1 progress: 5 of 5 steps done
  ✅ formatting, init, validate
  ✅ step 1 (variables)
  ✅ step 2 (resources)
  ✅ step 3 (outputs)
  ✅ step 4 (readme)
  ✅ step 5 (storage)
  ✅ earlier milestones still pass (M0)

👍 A1 passed. Next: run "Done when" in your own AWS account.

Full results: https://github.com/umbra-codex/aws-secure-file-upload/actions/runs/123456789
```

If any line shows ❌, the first one is marked `<- next`, and the last line names the step to fix.

It checks what you have **pushed**, not unsaved edits; if you have uncommitted changes or unpushed commits, it says so first. Nothing is saved on your machine: close the terminal and the results are still on GitHub. It needs the GitHub CLI, signed in (`gh auth login`).

**To re-check after a fix:** format, commit, and push. The push runs the check automatically. Run `scripts/remote-check.sh` only when you want a fresh run without pushing anything new.

The check runs A1 in five steps, one per file, so you can push after each file and see your progress:

| Step | Checks |
|---|---|
| 1 (variables) | `bucket/variables.tf`: the four inputs and their defaults |
| 2 (resources) | `bucket/main.tf`: the bucket and each of its settings |
| 3 (outputs) | `bucket/outputs.tf`: each output points at the right attribute |
| 4 (readme) | `bucket/README.md`: the sections and every input and output name |
| 5 (storage) | `buckets.tf` and `outputs.tf` in `modules/storage/`: the three module calls, their tags, and the storage outputs. It also checks every bucket name against S3's naming rule (3 to 63 characters; lowercase letters, numbers, dots, and hyphens), so you don't write that rule yourself. |

Steps you haven't reached yet show ❌; that's expected. You're done when every step is ✅ and the summary says `👍 Passed.`

Reading a failure:

- **"Resource not found: aws_s3_bucket.this"** or **"There is no managed resource ... in the root module"**: no resource with that exact type and name exists yet. Either you haven't built it or you named it differently, so check the block's type and name above. (The test treats the module it's testing as the "root module", so that wording is expected.)
- **"Module not installed"** or **"Unsupported argument"** in a module call: the module call's name or an input name doesn't match this brief.
- **An error like "Invalid function argument" pointing at a line in `tests/`**: the shape is wrong, not the value. Usually a missing `count`.
- **A row called `formatting (fmt -check)` is ❌ and lists file names**: the spacing or `=` alignment in those files isn't what `terraform fmt` produces. From the repo root run `terraform fmt -recursive`, then commit and push again. This row isn't one of the milestone's steps, but it fails the whole run on its own, so a green step table with a red formatting row still isn't done.
- **The summary shows only `formatting`, `init`, and `validate`, with no step rows**: `validate` failed, and the check stops there because no step can run on a configuration that doesn't validate. Read the `validate` output; it names the file and line.
- **Any other failed check** prints what it expected and what it got.

## Done when (in your own AWS account)

Run these from the repo root (the folder with `providers.tf` and `backend.hcl`), never from inside `modules/`. Run `init` again whenever a milestone adds or changes a module call.

```bash
terraform init -backend-config=backend.hcl
terraform apply
aws s3api get-bucket-versioning --bucket "$(terraform output -raw incoming_bucket_name)"
aws s3api get-bucket-versioning --bucket "$(terraform output -raw approved_bucket_name)"
echo "hello" | aws s3 cp - "s3://$(terraform output -raw incoming_bucket_name)/uploads/a1.txt"
aws s3api get-bucket-tagging --bucket "$(terraform output -raw incoming_bucket_name)"
terraform destroy
```
