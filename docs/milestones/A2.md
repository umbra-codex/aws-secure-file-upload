## Goal

Two things:

- **Files clean themselves up.** Raw uploads shouldn't sit in Incoming forever, and quarantined files only need keeping for a month. You'll teach the bucket module to expire objects after a set number of days.
- **The uploads table.** Every upload gets one row in DynamoDB. Lambda 1 writes it, Lambda 2 updates it, and the status endpoint reads it. The row layout is in the project overview's "DynamoDB item" contract.

Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't.

### main.tf

#### 2. The lifecycle rule (only when days are given)

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_lifecycle_configuration`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `count` | an expression, not a number: it gives `0` when the `expiration_days` variable is `null` and `1` otherwise |
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `rule` (nested block) | exactly one block, with everything below |
| `rule` → `id` | `"expire-objects"` |
| `rule` → `status` | `"Enabled"` |
| `rule` → `filter` (nested block) | an empty block, `filter {}`. Empty means "every object in the bucket". |
| `rule` → `expiration` (nested block) | one block with `days` = the `expiration_days` variable |
| `rule` → `noncurrent_version_expiration` (nested block) | one block with `noncurrent_days` = the `expiration_days` variable |
| `depends_on` | a list holding `aws_s3_bucket_versioning.this` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_lifecycle_configuration](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_lifecycle_configuration) · [depends_on](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on)

On a versioned bucket, deleting a file only hides it; the old version stays and keeps costing money. `noncurrent_version_expiration` cleans those up too. On a bucket without versioning (Quarantine), it has nothing to act on and does no harm, so keep it unconditional. `depends_on` makes Terraform finish versioning before it writes the lifecycle rule, which AWS's docs recommend for versioned buckets.

### dynamodb.tf (new file)

#### 5. The uploads table

**Block Type:** `resource`
**Resource Type:** `aws_dynamodb_table`
**Resource Name:** `uploads`

| Argument | Set To |
|---|---|
| `name` | the `project_name` variable followed by `-uploads` |
| `billing_mode` | `"PAY_PER_REQUEST"` |
| `hash_key` | `"upload_id"` |
| `attribute` (nested block) | exactly one block: `name` = `"upload_id"`, `type` = `"S"` |
| `ttl` (nested block) | one block: `attribute_name` = `"expires_at"`, `enabled` = `true` |
| `point_in_time_recovery` (nested block) | one block: `enabled` = `true` |
| `tags` | `Name` = the same expression you wrote for `name` (repeat it; don't reference the table's own `name`, which Terraform rejects as a cycle), `Role` = `"uploads"`, `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_dynamodb_table](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/dynamodb_table)

What each setting does:

- `PAY_PER_REQUEST` is on-demand pricing: no capacity to plan, and close to free when idle.
- `hash_key` is the partition key, the one attribute every lookup uses. Only declare attributes you use as keys; DynamoDB doesn't need the other columns declared.
- `ttl` lets DynamoDB delete rows whose `expires_at` time has passed. Lambda 1 sets `expires_at` on every row, and it must be a **Number** holding Unix epoch **seconds**. Lambda 2 (Portion D) removes it when an upload finishes, so only abandoned uploads get deleted. DynamoDB ignores strings and ISO dates, and it deletes expired rows within a day or two, not instantly.
- Point-in-time recovery keeps continuous backups, so the table can be restored to any second in the last 35 days.

Table names only need to be unique inside your own account and region, so there's no account ID in this one.

## Check it

### How to see your results

The check runs in two places. `scripts/check-local.sh` runs it on your machine at every checkpoint, and A1's [How to see your results](A1.md#how-to-see-your-results) explains that screen. GitHub runs it on every push, and the results are stored there: on the run's page under **Actions**, and on your pull request as the **ci** check.

**After a push (automatic):** open the repo on GitHub, click **Actions**, click the newest run, and scroll to **Summary**. The table lists every step with ✅ or ❌. Click **Output of the failed steps** under it to see what each ❌ expected and what it found.

**On GitHub, from your terminal:**

```bash
scripts/remote-check.sh
```

This follows the run your push started, waits for it if it is still running, and prints the same summary. When the milestone is complete, it looks like this:


It checks what you have **pushed**, not unsaved edits; if you have uncommitted changes or unpushed commits, it says so first. Nothing is saved on your machine: close the terminal and the results are still on GitHub. It needs the GitHub CLI, signed in (`gh auth login`).

**To re-check after a fix:** fix the file, run `scripts/check-local.sh` until the step is ✅, then format, commit, and push. The push runs the check on GitHub, and `scripts/remote-check.sh` follows that run.

A2 runs in four steps: 1 (expiration) the bucket module's expiration, 2 (storage) the two module-call arguments, 3 (table) the table and its outputs, 4 (readme) `expiration_days` in the module README. Every merged milestone is re-checked too, so A1 must still pass. See A1's [reading a failure](A1.md#check-it).

## Done when (in your own AWS account)

From the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
exec > >(tee ~/a2-done.txt) 2>&1
set -x
aws s3api get-bucket-lifecycle-configuration --bucket "$(terraform output -raw incoming_bucket_name)"
aws s3api get-bucket-lifecycle-configuration --bucket "$(terraform output -raw quarantine_bucket_name)"
aws dynamodb describe-table --table-name "$(terraform output -raw table_name)" \
  --query 'Table.{key: KeySchema, billing: BillingModeSummary.BillingMode}'
aws dynamodb describe-time-to-live --table-name "$(terraform output -raw table_name)"
aws dynamodb describe-continuous-backups --table-name "$(terraform output -raw table_name)" \
  --query 'ContinuousBackupsDescription.PointInTimeRecoveryDescription.PointInTimeRecoveryStatus'
terraform destroy
```

Expected: Incoming expires after 1 day and Quarantine after 30; the table's key is `upload_id`, billing is `PAY_PER_REQUEST`, TTL is enabled on `expires_at`, and point-in-time recovery says `ENABLED`. TTL switches on in the background, so right after `apply` it may say `ENABLING`; wait a minute and run that command again to see `ENABLED`. Asking for Approved's lifecycle configuration should return an error saying none exists.

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D a2-table
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/a2-table` ref.
