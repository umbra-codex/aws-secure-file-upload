## Goal

Block Public Access stops the buckets from becoming public. A bucket policy adds two more rules:

- **Every bucket refuses unencrypted connections.** Any request not made over HTTPS (TLS) is denied, so data is always encrypted in transit.
- **Nobody reads Quarantine** except the router (Lambda 2). Quarantined files may be malware, and keeping people away from them is one of the Well-Architected security principles.

Both rules are **Deny** statements. An explicit Deny beats any Allow, so they block data access even for account admins. (An admin can still delete the policy itself; this protects the data, not the configuration.) Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't.

## Part 1: The policy in the bucket module (`modules/storage/bucket/`)

### variables.tf

#### 1. The only allowed reader

**Block Type:** `variable`
**Variable Name:** `allowed_reader_arn`

| Argument | Set To |
|---|---|
| `description` | `"If set, deny s3:GetObject to every principal except this one."` |
| `type` | `string` |
| `default` | `null` |

**Tags:** variables don't take tags.

Add this variable before the dynamic block below; the block reads it, so `validate` fails until it exists.

**Docs:** [Input variables](https://developer.hashicorp.com/terraform/language/values/variables)

### main.tf

#### 2. The policy document

You could write the policy as raw JSON, but the `aws_iam_policy_document` data source lets you build it from blocks, checks it, and turns it into JSON for you.

**Block Type:** `data`
**Data Source Type:** `aws_iam_policy_document`
**Data Source Name:** `this`

First statement, always present:

| Argument | Set To |
|---|---|
| `statement` (nested block) | one block with everything below |
| `statement` → `sid` | `"DenyInsecureTransport"` |
| `statement` → `effect` | `"Deny"` |
| `statement` → `actions` | `["s3:*"]` |
| `statement` → `resources` | a list of two: the `arn` of `aws_s3_bucket.this`, and that same ARN followed by `/*` (use interpolation) |
| `statement` → `principals` (nested block) | one block: `type` = `"*"`, `identifiers` = `["*"]` |
| `statement` → `condition` (nested block) | one block: `test` = `"Bool"`, `variable` = `"aws:SecureTransport"`, `values` = `["false"]` |

Second statement, only when `allowed_reader_arn` is set. Write it as a `dynamic "statement"` block. A dynamic block has exactly two parts: `for_each`, then one `content { }` block. Every row marked `content →` goes inside `content`, and nothing else does. Write one dynamic block and no second literal `statement` block; the check counts statements.

| Argument | Set To |
|---|---|
| `for_each` (on the dynamic block) | an empty list when the `allowed_reader_arn` variable is `null`, otherwise a one-item list holding it |
| `content` → `sid` | `"DenyReadsExceptAllowedReader"` |
| `content` → `effect` | `"Deny"` |
| `content` → `actions` | `["s3:GetObject"]` |
| `content` → `resources` | a one-item list: the bucket's `arn` followed by `/*` |
| `content` → `principals` (nested block) | one block: `type` = `"*"`, `identifiers` = `["*"]` |
| `content` → `condition` (nested block) | one block: `test` = `"StringNotEquals"`, `variable` = `"aws:PrincipalArn"`, `values` = a one-item list holding `statement.value` |

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [dynamic blocks](https://developer.hashicorp.com/terraform/language/expressions/dynamic-blocks)

How to read the policy:

- The bucket ARN alone means the bucket itself; the ARN followed by `/*` means every object in it. The TLS rule covers both.
- `aws:SecureTransport` is `"false"` when a request didn't use HTTPS, so the first statement denies exactly those requests.
- The second statement denies `GetObject` to everyone whose ARN is **not** the allowed reader (`StringNotEquals`). It blocks *reading* files. Listing the file names (`s3:ListBucket`) is a separate action and isn't blocked; the goal here is protecting file contents.
- `statement` is the dynamic block's iterator. Terraform names it after the block's label, so don't rename it with `iterator`. `statement.value` is the current item from `for_each`, and it only exists inside `content`.

#### 3. Attach the policy

**Block Type:** `resource`
**Resource Type:** `aws_s3_bucket_policy`
**Resource Name:** `this`

| Argument | Set To |
|---|---|
| `bucket` | the `id` of `aws_s3_bucket.this` |
| `policy` | the `json` attribute of `data.aws_iam_policy_document.this` |
| `depends_on` | a list holding `aws_s3_bucket_public_access_block.this` |

**Tags:** not supported by this resource type.

**Docs:** [aws_s3_bucket_policy](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/s3_bucket_policy) · [depends_on](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on)

S3 can reject a policy write that happens while its Block Public Access settings are still being written. `depends_on` makes Terraform finish one before starting the other.

## Check it

### How to see your results

The check runs in two places. `scripts/check-local.sh` runs it on your machine at every checkpoint, and A1's [How to see your results](A1.md#how-to-see-your-results) explains that screen. GitHub runs it on every push, and the results are stored there: on the run's page under **Actions**, and on your pull request as the **ci** check.

**After a push (automatic):** open the repo on GitHub, click **Actions**, click the newest run, and scroll to **Summary**. The table lists every step with ✅ or ❌. Click **Output of the failed steps** under it to see what each ❌ expected and what it found.

**On GitHub, from your terminal:**

```bash
scripts/remote-check.sh
```

This follows the run your push started, waits for it if it is still running, and prints the same summary. When the milestone is complete, it looks like this:

```
Checking the last commit you pushed to a3-bucket-policies (3f2c1ab)
Looking for the run your push started...
Run finished in 58s

A3: 3 of 3 steps done
  ✅ formatting, init, validate
  ✅ step 1 (policy)
  ✅ step 2 (storage)
  ✅ step 3 (readme)
  ✅ earlier milestones still pass (M0, A1, A2)

👍 A3 passed.

Full results: https://github.com/umbra-codex/aws-secure-file-upload/actions/runs/123456789
```

If any line shows ❌, the first one is marked `<- next`, and the last line names the step to fix.

It checks what you have **pushed**, not unsaved edits; if you have uncommitted changes or unpushed commits, it says so first. Nothing is saved on your machine: close the terminal and the results are still on GitHub. It needs the GitHub CLI, signed in (`gh auth login`).

**To re-check after a fix:** fix the file, run `scripts/check-local.sh` until the step is ✅, then format, commit, and push. The push runs the check on GitHub, and `scripts/remote-check.sh` follows that run.

A3 runs in three steps: 1 (policy) the variable, policy document, bucket policy, and output; 2 (storage) the Quarantine lock; 3 (readme) `allowed_reader_arn` in the module README. A1 and A2 must still pass. See A1's [reading a failure](A1.md#check-it).

## Done when (in your own AWS account)

From the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
aws s3api get-bucket-policy --bucket "$(terraform output -raw quarantine_bucket_name)" --query Policy --output text
echo "test" | aws s3 cp - "s3://$(terraform output -raw quarantine_bucket_name)/a3.txt"
aws s3 cp "s3://$(terraform output -raw quarantine_bucket_name)/a3.txt" -
aws s3 rm "s3://$(terraform output -raw quarantine_bucket_name)/a3.txt"
terraform destroy
```

Expected: the policy shows both statements; writing the test file works; **reading it back fails with AccessDenied**, even as your admin user, because you aren't the router; deleting it works. If D2 is already merged, its synthetic test must still pass with A3 applied.

Add `A3` to `milestones.txt`, then format, commit, and push:

```bash
terraform fmt -recursive
git add -A && git commit -m "chore(a3): add A3 to milestones.txt" && git push
```

Before you mark it ready, check GitHub once. `scripts/remote-check.sh` follows the run your last push started and prints the same summary, and it needs no new commit or push ([A1](A1.md#how-to-see-your-results) explains the output):

```bash
scripts/remote-check.sh
```

Paste the "Done when" output into your draft PR. The repo is squash-only, so the PR's title becomes the commit on `main`, and `--fill` named it after your first checkpoint. Retitle it to the whole milestone, then mark it ready (see A1's [Mark the pull request ready](A1.md#mark-the-pull-request-ready)):

```bash
gh pr edit --title "feat(a3): add bucket policies"
gh pr ready
```

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D a3-bucket-policies
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/a3-bucket-policies` ref.
