## Goal

After uploading, the client asks "what happened to my file?" by calling `GET /status/{upload_id}`. You build what answers it:

- **A small Lambda function** (Python) that looks up one row in the uploads table and returns its status.
- **An IAM role** that lets the function read that table and write its logs, and nothing else.
- **A route on the team's HTTP API** (built by B in B2) that sends `GET /status/{upload_id}` to your function.

It's the first milestone with application code, and the first that plugs into another portion's work. Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't.

## Part 1: The function's code (`modules/status/src/handler.py`)

This milestone's code lives inside the module, in a `src` folder, so the module carries everything it needs. Create the folder and the file.

#### 1. What the handler must do

Write one function named `handler` that takes two arguments, `event` and `context`. That's the entry point Lambda calls on every request.

| Step | Behavior |
|---|---|
| 1 | Read `upload_id` from the request: the event's `pathParameters`, key `upload_id`. If it's missing, return status code `400`. |
| 2 | Read the table name from the `TABLE_NAME` environment variable (`os.environ`). Never hardcode it. |
| 3 | Look up the row with `get_item`, using `upload_id` as the key. That's a direct key lookup; never scan the table. |
| 4 | If there's no row, return `404` with a short error message. |
| 5 | If the row's `status` is `PENDING` but its `expires_at` (Unix seconds) is in the past, report `EXPIRED` instead. The row itself isn't changed. |
| 6 | Otherwise return `200` with a JSON body holding `upload_id`, `status`, and `reason` when the row has one. |

**Use the DynamoDB *resource* interface,** not the low-level client: `boto3.resource("dynamodb").Table(...)`, then `get_item` on that table. It returns plain Python values: `status` is a string, and `expires_at` is a `Decimal`, so convert it with `int()` before comparing it to the current time. The low-level client (`boto3.client("dynamodb")`) wraps every value (`{"S": "PENDING"}`), which silently breaks the status and expiry logic. `boto3` is already installed in the Lambda Python runtime, so there's nothing to package.

**Every response is a dictionary** with three keys: `statusCode` (a number), `headers` (`{"Content-Type": "application/json"}`), and `body` (your JSON, converted to a string with `json.dumps`). Return the dictionary itself. Only the `body` value goes through `json.dumps`; returning `json.dumps` of the whole dictionary gives API Gateway a string, and the call fails with a 502.

**Tags:** not applicable (this is code, not a Terraform block).

**Docs:** [Python Lambda handlers](https://docs.aws.amazon.com/lambda/latest/dg/python-handler.html) · [boto3 Table.get_item](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/dynamodb/table/get_item.html) · [HTTP API Lambda payload format 2.0](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-lambda.html)

## Part 3: Permissions (`modules/status/iam.tf`, new file)

A Lambda function runs as an **IAM role**. Two documents decide what that role can do, and they're easy to mix up:

- **The trust policy** answers *who is allowed to use this role*. Here that's the Lambda service (`lambda.amazonaws.com`), and the action it performs is `sts:AssumeRole`: the service asks AWS for temporary credentials to run your function as this role. You don't create the trust policy as its own object. You pass its JSON to the role's `assume_role_policy` argument (section 4), so there's no separate "attach" step for it.
- **The permissions policy** answers *what the role may do* once it's in use. Yours allows reading one table and writing to one log group.

You attach the permissions with `aws_iam_role_policy`, an **inline** policy: it lives inside the role and is deleted with it. (Tutorials often show `aws_iam_policy` plus `aws_iam_role_policy_attachment`; that pair is for standalone policies shared by many roles. One role with one job is what inline is for.) Note that `logs:CreateLogGroup` isn't in the permissions: Terraform already created the log group in Part 2, so the function only creates log streams inside it.
