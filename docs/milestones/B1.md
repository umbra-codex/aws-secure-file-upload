## Goal

Every upload starts with a client asking "may I upload this file?" Lambda 1 answers. In this milestone you build it:

- **A Lambda function** (Python) that checks the request, records it in the uploads table as `PENDING`, and hands back a **presigned POST**: a signed form that lets the client upload one file, to one key, for 15 minutes, straight to the Incoming bucket.
- **An IAM role** that lets the function sign that upload, write that one row, and write its logs, and nothing else.
- **Structured logs**: every log line is JSON and carries the `upload_id`, so one upload can be traced from start to finish.

The API in front of it comes in B2. Here you test the function by invoking it directly. Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't, and skim A4's brief: its status function, built after B2, follows the same pattern.

## Part 1: The function's code (`modules/upload_api/src/handler.py`)

The code lives inside the module, in a `src` folder, so the module carries everything it needs. Create the folder and the file.

#### 1. What the handler must do

Write one function, `def handler(event, context):`, written exactly like that (the check matches the line). Lambda calls it on every request. The request arrives the way API Gateway will send it in B2: a JSON string in the event's `body`, holding three fields:

```json
{"filename": "cat.png", "content_type": "image/png", "size": 48213}
```

`size` is the file's size in bytes. The handler does this, in this order:

| Step | Behavior |
|---|---|
| 1 | Read four settings from environment variables (`os.environ`), once, at the top of the file: `TABLE_NAME`, `BUCKET_NAME`, `ALLOWED_TYPES` (a comma-separated string, so `split(",")` it into a list), and `MAX_SIZE_MB` (a string, so `int()` it). Never hardcode any of them. |
| 2 | Read the request from `event["body"]`. If the event's `isBase64Encoded` is true, base64-decode the body first. Parse it with `json.loads`. If it isn't valid JSON, or isn't a JSON object, return `400`. |
| 3 | Read `filename`, `content_type`, and `size`. If `filename` or `content_type` isn't a string, or `size` isn't a whole number, return `400`. (Python treats `True` as the number 1, so check `type(size) is int`, not `isinstance`.) |
| 4 | Return `400` if `content_type` isn't in the allowed list, or if `size` is below 1 or above `MAX_SIZE_MB` × 1024 × 1024 bytes. |
| 5 | Clean the filename: drop control characters (code points below 32, and 127), remove every `/` and `\`, remove `..` until none is left (removing it once can create a new one), and cut the result to 100 characters. If nothing is left, return `400`. |
| 6 | Create `upload_id` with `str(uuid.uuid4())`. |
| 7 | Write the row with `put_item`: `upload_id`, `filename` (the cleaned one), `declared_type`, `declared_size`, `status` = `"PENDING"`, `created_at` (the current UTC time as ISO 8601: `datetime.now(timezone.utc).isoformat()`), and `expires_at` = the current Unix time + 900 + 3600, as a whole number. Don't catch errors from `put_item`: if the write fails, the invocation should fail, which is what B3's alarm watches for. |
| 8 | Sign the upload with `generate_presigned_post`: `Bucket` = the bucket name, `Key` = `uploads/{upload_id}/{cleaned filename}`, `ExpiresIn` = `900`. |
| 9 | Log it, on one line: `logger.info("upload url issued", extra={"upload_id": upload_id})`, where `logger = logging.getLogger()`. |
| 10 | Return `200` with a JSON body holding `upload_id`, `url` and `fields` (both from the presigned POST), and `expires_in` = `900`. |

Every `400` returns a JSON body like `{"error": "content_type is not allowed"}`: a short reason the client can act on. Log those too, with `logger.warning`.

**Two different boto3 interfaces, on purpose.** Use the DynamoDB *resource* interface for the row, as in A4: `boto3.resource("dynamodb").Table(...)`, then `put_item` with plain Python values. It accepts `int` but rejects `float`, which is why `expires_at` must be `int(time.time()) + ...` and not `time.time() + ...`. Use the S3 *client* for signing: `boto3.client("s3").generate_presigned_post(...)` returns a dictionary with `url` and `fields`. `boto3` is already installed in the Lambda Python runtime, so there's nothing to package.

**The key is locked for you.** When you pass a `Key`, boto3 adds a condition that the upload's key must be exactly that key, so the file can only land in `uploads/{upload_id}/`. Don't add your own key condition; boto3's docs say key conditions are filled in for you. B2 adds the one condition boto3 doesn't: the size limit.

**`expires_at` must be a Number.** DynamoDB's TTL (set up in A2) only reads Unix seconds stored as a Number. It deletes the row an hour after the upload window closes, if nothing finished it. That's 900 seconds for the window plus 3600 for the hour.

**Every response is a dictionary** with three keys: `statusCode` (a number), `headers` (`{"Content-Type": "application/json"}`), and `body` (your JSON, converted to a string with `json.dumps`). Return the dictionary itself; only the `body` value goes through `json.dumps`. This is the same shape as A4.

**Docs:** [boto3 generate_presigned_post](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/s3/client/generate_presigned_post.html) · [Presigned URLs and POSTs (boto3 guide)](https://boto3.amazonaws.com/v1/documentation/api/latest/guide/s3-presigned-urls.html) · [boto3 Table.put_item](https://boto3.amazonaws.com/v1/documentation/api/latest/reference/services/dynamodb/table/put_item.html) · [Logging extra fields in JSON (Lambda)](https://docs.aws.amazon.com/lambda/latest/dg/python-logging.html#python-logging-extra) · [uuid](https://docs.python.org/3/library/uuid.html) · [HTTP API Lambda payload format 2.0](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-develop-integrations-lambda.html)

## Part 3: Permissions (`modules/upload_api/iam.tf`, new file)

Same pattern as A4's Part 3: a **trust policy** (who may use the role: the Lambda service) passed to the role's `assume_role_policy`, and a **permissions policy** (what the role may do) attached as an inline `aws_iam_role_policy`. Read A4's [Part 3](A4.md#part-3-permissions-modulesstatusiamtf-new-file) if either idea is new.

**Why a role that never uploads needs `s3:PutObject`.** A presigned POST is signed with the role's credentials. When the client uploads, S3 checks the signature and then checks whether *the signer* is allowed to put that object. If the role can't, every upload fails with AccessDenied, even though the URL looked fine. The permission is scoped to `uploads/*`, so a leaked form can never write anywhere else in the bucket.

## Done when (in your own AWS account)

These commands need the AWS CLI v2: `aws --version` should start with `aws-cli/2.`. Version 1 has no `aws logs tail` and no `--cli-binary-format`.

Run the commands one at a time. A command that runs over several lines (ending in `\`, or a `{ ... }` block) goes in whole. `apply` and `destroy` each stop and ask you to type `yes`, and `destroy` is finished when it prints `Destroy complete!`.

From the repo root:

```bash
terraform init -backend-config=backend.hcl
mkdir -p .evidence
exec > >(tee .evidence/b1-done.txt) 2>&1
set -x
terraform apply
FN=$(terraform output -raw upload_function_name)
TABLE=$(terraform output -raw table_name)

# A valid request: expect statusCode 200
aws lambda invoke --function-name "$FN" --cli-binary-format raw-in-base64-out \
  --payload '{"body": "{\"filename\": \"cat.png\", \"content_type\": \"image/png\", \"size\": 1024}"}' /dev/stdout; echo

# The row it wrote: expect one line ending in PENDING
aws dynamodb scan --table-name "$TABLE" \
  --query 'Items[].[upload_id.S, filename.S, expires_at.N, status.S]' --output text

# A type that isn't allowed: expect statusCode 400
aws lambda invoke --function-name "$FN" --cli-binary-format raw-in-base64-out \
  --payload '{"body": "{\"filename\": \"page.html\", \"content_type\": \"text/html\", \"size\": 10}"}' /dev/stdout; echo

# The structured log line: expect JSON containing "upload_id"
aws logs tail "/aws/lambda/$FN" --since 10m | grep upload_id

terraform destroy
```

Expected:

1. A response like `{"statusCode": 200, "headers": {...}, "body": "{\"upload_id\": \"6f1c...\", \"url\": \"https://...\", \"fields\": {\"key\": \"uploads/6f1c.../cat.png\", ...}, \"expires_in\": 900}"}`, followed by the CLI's own `{"StatusCode": 200, ...}`. The first status code is your handler's; the second only means Lambda ran it.
2. One line: the same `upload_id`, `cat.png`, a number about 75 minutes in the future, `PENDING`.
3. `"statusCode": 400` with an `error` message in the body.
4. A JSON line with `"message": "upload url issued"` and your `upload_id`.

The scan reads the whole table, which is fine for a test table with one row; the code itself must never scan. `/dev/stdout` prints the response instead of saving a file into the repo. If the first call returns `"errorMessage"` instead of a status code, the handler crashed: `aws logs tail "/aws/lambda/$FN" --since 10m` shows the error. `AccessDeniedException` on `PutItem` means the second statement's resource doesn't match the table. If nothing at all reaches the log group, check that `log_group` in `logging_config` names it. If `apply` fails with `The role defined for the function cannot be assumed by Lambda`, the new role hasn't spread through IAM yet: wait a few seconds and run `terraform apply` again.

The `url` and `fields` work as an upload form already; B2 adds the size limit and tries a real upload.


## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D b1-upload-lambda
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/b1-upload-lambda` ref.
