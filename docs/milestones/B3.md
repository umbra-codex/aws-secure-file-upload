## Goal

The pipeline works. Now the team needs to see it working, and notice when it isn't. You build:

- **Throttling** on the API, so a flood of requests is turned away at the door instead of running up Lambda and DynamoDB.
- **CORS** on the API, so a web page on an origin you list can call it from a browser.
- **Two alarms** that flip when Lambda 1 or Lambda 2 returns an error.
- **One CloudWatch dashboard** with the whole pipeline on one screen: scan results, Lambda errors and duration, both failure queues, and API errors.

It's the last milestone before INT (the team's final end-to-end test), and it reads values from C and D, which is why it waits for C2 and D2. Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't.

## Part 2: Throttling and CORS (`modules/upload_api/api.tf`)

Both are new nested blocks inside resources you built in B2.

#### 3. Throttling on the stage

Add this nested block to `aws_apigatewayv2_stage.default`:

| Argument | Set To |
|---|---|
| `default_route_settings` (nested block) | one block with the two rows below |
| `default_route_settings` → `throttling_burst_limit` | `10` |
| `default_route_settings` → `throttling_rate_limit` | `5` |

**Docs:** [aws_apigatewayv2_stage](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/apigatewayv2_stage) · [Throttling for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html)

API Gateway throttles with a **token bucket**: the bucket holds up to 10 requests (the burst) and refills at 5 per second (the rate). A request that finds the bucket empty gets `429 Too Many Requests` and never reaches Lambda. `default_route_settings` applies to every route on the stage, including A4's status route. These numbers are deliberately small: a demo pipeline needs a few requests a second, and small limits are easy to see in "Done when".

#### 4. CORS on the API

Add this nested block to `aws_apigatewayv2_api.this`:

| Argument | Set To |
|---|---|
| `cors_configuration` (nested block) | one block with the four rows below |
| `cors_configuration` → `allow_origins` | the `cors_allowed_origins` variable |
| `cors_configuration` → `allow_methods` | `["GET", "POST"]` |
| `cors_configuration` → `allow_headers` | `["content-type"]` |
| `cors_configuration` → `max_age` | `300` |

**Docs:** [aws_apigatewayv2_api](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/apigatewayv2_api) · [CORS for HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html)

A browser won't let a page on one origin read a response from another unless the server says it may. Before a `POST` with a JSON body, the browser first sends an `OPTIONS` request (a **preflight**) asking "may this origin send a POST with a `content-type` header?" With `cors_configuration` set, API Gateway answers preflights itself, without calling your Lambda. `GET` is there for A4's status route; `max_age` lets the browser remember the answer for 5 minutes.

## Part 3: Error alarms (`modules/upload_api/alarms.tf`, new file)

A **CloudWatch alarm** watches one metric and changes state when it crosses a threshold: `OK`, `ALARM`, or `INSUFFICIENT_DATA`. Lambda publishes an `Errors` metric for every function, counting invocations that failed (an unhandled exception, a timeout, or a crash). Your two alarms watch it.

#### 5. Lambda 1's alarm

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_metric_alarm`
**Resource Name:** `upload_url_errors`

| Argument | Set To |
|---|---|
| `alarm_name` | the `project_name` variable followed by `-upload-url-errors` |
| `alarm_description` | a short sentence saying what it means |
| `namespace` | `"AWS/Lambda"` |
| `metric_name` | `"Errors"` |
| `dimensions` | a map with one entry: `FunctionName` = the `function_name` of `aws_lambda_function.upload_url` |
| `statistic` | `"Sum"` |
| `period` | `60` |
| `evaluation_periods` | `1` |
| `threshold` | `1` |
| `comparison_operator` | `"GreaterThanOrEqualToThreshold"` |
| `treat_missing_data` | `"notBreaching"` |
| `tags` | `Name` = the same expression you wrote for `alarm_name`, repeated; `Role` = `"observability"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_cloudwatch_metric_alarm](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_metric_alarm) · [Lambda function metrics](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-metrics-types.html) · [How alarms evaluate](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation.html)

Read together: "add up the errors in each 60-second window, and go to `ALARM` if one window has 1 or more." A metric only has data points when something happens, so a quiet function has *missing* data. `notBreaching` treats that silence as healthy; without it, the alarm sits in `INSUFFICIENT_DATA` most of the time.

#### 6. Lambda 2's alarm

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_metric_alarm`
**Resource Name:** `router_errors`

Every argument is the same as section 5, except these three:

| Argument | Set To |
|---|---|
| `alarm_name` | the `project_name` variable followed by `-router-errors` |
| `dimensions` | a map with one entry: `FunctionName` = the `router_function_name` variable |
| `tags` | `Name` = the same expression you wrote for `alarm_name`, repeated; `Role` = `"observability"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_cloudwatch_metric_alarm](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_metric_alarm)

Lambda 2 belongs to D, so you get its name through the `router_function_name` variable that the root already passes in. The alarms have no actions: they change state in CloudWatch and nobody is emailed. Watch them on the CloudWatch **Alarms** page, or from the CLI as in "Done when" step 4; the dashboard shows metrics, not alarm state. C's alert topic covers malware and scanner errors.

## Part 4: The dashboard (`modules/upload_api/dashboard.tf`, new file)

A **CloudWatch dashboard** is one JSON document, the **dashboard body**, that lists **widgets**. Each widget here is a graph of one or more metrics. You write the body as a Terraform object and turn it into JSON with `jsonencode`, the same way you built B2's access log format.

#### 7. The current region

**Block Type:** `data`
**Data Source Type:** `aws_region`
**Data Source Name:** `current`

No arguments. Its `region` attribute is the region Terraform is deploying into (for example `us-east-1`).

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_region](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/region)

Every graph widget must say which region its metrics come from. Reading it from the provider means the dashboard works in whatever region a teammate deploys to. (Older examples use this data source's `name` attribute; in this provider version it's `region`.)

#### 8. The dashboard

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_dashboard`
**Resource Name:** `pipeline`

| Argument | Set To |
|---|---|
| `dashboard_name` | the `project_name` variable followed by `-pipeline` |
| `dashboard_body` | `jsonencode` of an object with one key, `widgets`: a list of the five widgets below |

**Tags:** not supported by this resource type.

**Docs:** [aws_cloudwatch_dashboard](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_dashboard) · [Dashboard body structure](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/CloudWatch-Dashboard-Body-Structure.html) · [Metric widget properties](https://docs.aws.amazon.com/AmazonCloudWatch/latest/APIReference/CloudWatch-Dashboard-Body-Structure.html#CloudWatch-Dashboard-Properties-Metric-Widget-Object)

**The shape of one widget.** Here's a graph of an unrelated metric, in the JSON form the AWS docs use, so you can see the structure:

```json
{
  "type": "metric",
  "x": 0, "y": 0, "width": 12, "height": 6,
  "properties": {
    "title": "EC2 CPU",
    "region": "us-east-1",
    "stat": "Average",
    "period": 300,
    "metrics": [
      ["AWS/EC2", "CPUUtilization", "InstanceId", "i-0123456789abcdef0"]
    ]
  }
}
```

`x`, `y`, `width`, and `height` place the widget on a grid 24 units wide. Each line in `metrics` is a list: namespace, metric name, then dimension name and value pairs. In Terraform, write each widget as an object (`key = value`) inside the `widgets` list; `jsonencode` produces the JSON.

**The five widgets.** Every widget has `type` = `"metric"`, `width` = `12`, `height` = `6`, and `region` = the `region` of `data.aws_region.current`.

| # | `x`, `y` | `title` | `stat` | `period` | `metrics` (one line each) |
|---|---|---|---|---|---|
| 1 | 0, 0 | `"GuardDuty scan results"` | `"Sum"` | `300` | four search lines, see below |
| 2 | 12, 0 | `"Lambda errors"` | `"Sum"` | `60` | `AWS/Lambda` `Errors` `FunctionName` = Lambda 1's `function_name`; the same for the `router_function_name` variable |
| 3 | 0, 6 | `"Lambda duration"` | `"Average"` | `60` | `AWS/Lambda` `Duration` `FunctionName` = Lambda 1's `function_name`; the same for the `router_function_name` variable |
| 4 | 12, 6 | `"Failure queue depth"` | `"Maximum"` | `60` | `AWS/SQS` `ApproximateNumberOfMessagesVisible` `QueueName` = the `dlq_name` variable; the same for the `router_failures_queue_name` variable |
| 5 | 0, 12 | `"API errors"` | `"Sum"` | `60` | `AWS/ApiGateway` `4xx` `ApiId` = the `id` of `aws_apigatewayv2_api.this`; the same with `5xx` |

**Widget 1 uses search expressions.** GuardDuty publishes its scan counts to the namespace `AWS/GuardDuty/MalwareProtection`, one set per protection plan, and your module doesn't know C's plan ID. A **search expression** finds every matching metric for you. Instead of a namespace-and-name list, each of the four lines is a list holding one object with `expression`, `id`, and `label`:

| `id` | `label` | `expression` |
|---|---|---|
| `"completed"` | `"Completed"` | `SEARCH('{AWS/GuardDuty/MalwareProtection} MetricName="CompletedScanCount"', 'Sum', 300)` |
| `"infected"` | `"Threats found"` | the same, with `InfectedScanCount` |
| `"skipped"` | `"Skipped"` | the same, with `SkippedScanCount` |
| `"failed"` | `"Failed"` | the same, with `FailedScanCount` |

The expression contains double quotes, so inside a Terraform string each `"` around the metric name is written `\"`. The single quotes stay as they are.

**Docs:** [GuardDuty S3 scan metrics](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-cloudwatch-metrics-s3-malware-protection.html) · [Search expressions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/search-expression-syntax.html) · [HTTP API metrics](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-metrics.html) · [SQS metrics](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-available-cloudwatch-metrics.html)

`ApproximateNumberOfMessagesVisible` is how many failed events are waiting in a queue. Both queues should sit at zero; anything else means events need a look and a redrive (D4). `Maximum` shows the worst moment in each minute, so a short spike isn't averaged away.

## Done when (in your own AWS account)

First set one origin in your `terraform.tfvars`, so there's something for CORS to allow:

```hcl
cors_allowed_origins = ["http://localhost:3000"]
```

These commands need the AWS CLI v2: `aws --version` should start with `aws-cli/2.`. Version 1 has no `aws logs tail` and no `--cli-binary-format`. Then, from the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
exec > >(tee ~/b3-done.txt) 2>&1
set -x
API=$(terraform output -raw api_url); API=${API%/}
FN=$(terraform output -raw upload_function_name)
DASH=$(terraform output -raw dashboard_name)
BUCKET=$(terraform output -raw incoming_bucket_name)   # for step 3
T=$(mktemp -d)                                         # for step 3

# 1. CORS: expect access-control-allow-origin: http://localhost:3000
curl -s -i -X OPTIONS "$API/upload-url" -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type" | grep -i '^access-control'

# 2. Throttling: 40 requests at once: expect some 429 among the 400s
(for i in $(seq 40); do curl -s -o /dev/null -w "%{http_code}\n" -X POST "$API/upload-url" -d '{}' & done; wait) | sort | uniq -c

# 3. A test upload: run B2's "Done when" steps 1 and 2 (BUCKET and T are set above),
#    wait about 10 minutes, then expect GuardDuty's scan-count metric names
aws cloudwatch list-metrics --namespace AWS/GuardDuty/MalwareProtection --query 'Metrics[].MetricName' --output text
echo "Open CloudWatch > Dashboards > $DASH"

# 4. A forced Lambda error: remove Lambda 1's permissions (B1 named the role and its policy
#    after the function), call it, expect 500
aws iam delete-role-policy --role-name "$FN" --policy-name "$FN"
sleep 20
curl -s -w "\n%{http_code}\n" -X POST "$API/upload-url" -H "Content-Type: application/json" \
  -d '{"filename": "cat.png", "content_type": "image/png", "size": 1024}'

#    ...then wait for the alarm: expect ALARM within about 3 minutes
for i in $(seq 30); do
  A=$(aws cloudwatch describe-alarms --alarm-names "${FN}-errors" --query 'MetricAlarms[0].StateValue' --output text)
  [ "$A" = ALARM ] && break
  sleep 20
done
echo "alarm state: $A"

#    ...and put the permissions back: expect "1 to add" (the inline policy)
terraform apply

# Incoming is versioned and holds the test upload from step 3: remove every version and delete marker, or destroy fails
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' --output json)"

rm -r "$T"
terraform destroy
```

Expected: (1) `access-control-allow-origin: http://localhost:3000` and the allowed methods; (2) counts of `400` and `429` (the `400`s are your handler refusing `{}`; the `429`s never reached it); (3) the scan-count metric names GuardDuty publishes for your plan (for example `CompletedScanCount`), and on the dashboard a point in **GuardDuty scan results** and in **Lambda duration**; (4) `{"message":"Internal Server Error"}` with `500`, then `alarm state: ALARM`, then a plan that adds the policy back. Take a screenshot of the dashboard for your PR.

Step 4 is a real outage, on purpose: without its policy, Lambda 1 can't write the row, `put_item` raises, and the invocation fails. That's the `Errors` metric your alarm watches, and it's why B1's handler never catches that error. Running `terraform apply` afterward is how Terraform repairs **drift**: it compares your code with what's in AWS and puts back what's missing.

Things that commonly go wrong:

- **No `access-control-allow-origin` line**: the origin in the request doesn't exactly match one in `cors_allowed_origins` (scheme and port count), or `upload_api.tf` doesn't pass the variable in.
- **No `429` at all**: run step 2 again; 40 requests in parallel should beat a burst of 10, but a slow connection spreads them out.
- **`apply` fails with `The dashboard body is invalid`**: the body isn't the shape above. Common causes: a widget missing `region`, a `metrics` line that isn't a list, or an unescaped `"` inside a `SEARCH(...)` string.
- **A widget says "No data"**: usually a wrong dimension name or value (`FunctionName`, `QueueName`, `ApiId`), not a wrong metric. Compare it with the real name in the Lambda, SQS, or API Gateway console.
- **An empty GuardDuty widget**: metrics appear only after the first scan. Check that C1's plan is active and give it 10 minutes.
- **The loop in step 4 gives up after 10 minutes without `ALARM`**: check that step 4's `curl` returned `500`. If it returned `200`, the policy deletion hadn't taken effect yet; wait and call again.

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D b3-observability
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/b3-observability` ref.
