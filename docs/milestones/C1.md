## Goal

Every file a client uploads lands in the Incoming bucket, and none of it can be trusted yet. In this milestone you turn on **GuardDuty Malware Protection for S3**, an AWS service that scans each new file for malware, so the pipeline never has to run a scanner of its own. You build two things:

- **An IAM role** that GuardDuty uses to read each new file, tag it with the result, and manage the EventBridge plumbing it needs. AWS publishes the exact permissions; you copy them into Terraform instead of writing them from memory.
- **A malware protection plan**: the switch that connects that role to the Incoming bucket. It scans only files under `uploads/` and writes the result onto each file as an S3 tag.

Scan results also arrive as EventBridge events. C2 listens for them; here you only turn the scanner on and check it works. This is one of the security-heavy milestones, so plan time for the review. Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't.

Two facts about the service shape everything below:

- **It works without a GuardDuty detector.** [Malware Protection for S3](https://docs.aws.amazon.com/guardduty/latest/ug/gdu-malware-protection-s3.html) runs as its own feature. You don't enable GuardDuty itself, and the plan won't clash with an account that already has GuardDuty on. The signals you get are the tag and the EventBridge event, not a GuardDuty finding.
- **It is billed by usage.** AWS bills for the data scanned and the number of objects, and gives each account a monthly free tier (1,000 requests and 1 GB scanned per Region at the time of writing); turning tagging on adds a small S3 charge too. See [pricing](https://docs.aws.amazon.com/guardduty/latest/ug/pricing-malware-protection-for-s3-guardduty.html). "Done when" scans two tiny files, but don't point real data at your test deployment.

## Part 1: The role and its permissions (`modules/scanning/iam.tf`, new file)

An IAM **role** is an identity that a service can borrow. Two documents define it. The **trust policy** says who may borrow it (here, GuardDuty's malware protection service). The **permissions policy** says what the borrower may do. You write both as `aws_iam_policy_document` data sources, which turn Terraform blocks into the JSON that IAM expects, and attach them to the role. Read the [IAM roles page](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html) if the idea is new.

AWS gives you both documents on one page: [Create or update IAM role policy](https://docs.aws.amazon.com/guardduty/latest/ug/malware-protection-s3-iam-policy-prerequisite.html). Keep it open next to this brief. The tables below say what to write; the page says why, and it's the source if you want to double-check a value.

#### 1. Your account and region

**Block Type:** `data`
**Data Source Type:** `aws_caller_identity`
**Data Source Name:** `current`

No arguments. Its `account_id` attribute is the ID of the AWS account Terraform is running in.

**Block Type:** `data`
**Data Source Type:** `aws_region`
**Data Source Name:** `current`

No arguments. Its `region` attribute is the region Terraform is deploying into (for example `us-east-1`). (Older examples use `name`; in this provider version it's `region`.)

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_caller_identity](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/caller_identity) · [aws_region](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/region)

GuardDuty creates an EventBridge rule of its own in your account, and the permissions below have to name that rule's ARN, which contains your region and account ID. Reading both from the provider keeps the code working in any account and region.

#### 2. Who may use the role (trust policy)

**Block Type:** `data`
**Data Source Type:** `aws_iam_policy_document`
**Data Source Name:** `assume`

| Argument | Set To |
|---|---|
| `statement` (nested block) | exactly one block with the rows below |
| `statement` → `effect` | `"Allow"` |
| `statement` → `actions` | `["sts:AssumeRole"]` |
| `statement` → `principals` (nested block) | one block: `type` = `"Service"`, `identifiers` = `["malware-protection-plan.guardduty.amazonaws.com"]` |

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [AWS's trust policy](https://docs.aws.amazon.com/guardduty/latest/ug/malware-protection-s3-iam-policy-prerequisite.html#add-iam-trust-policy-s3-malware-protection)

The principal is a service, not a user: `sts:AssumeRole` is the action a service calls to borrow the role. Note the service name. It is GuardDuty's malware protection service, not `guardduty.amazonaws.com`.

#### 3. The role

**Block Type:** `resource`
**Resource Type:** `aws_iam_role`
**Resource Name:** `guardduty`

| Argument | Set To |
|---|---|
| `name` | the `project_name` variable followed by `-guardduty` |
| `assume_role_policy` | the `json` of `data.aws_iam_policy_document.assume` |
| `tags` | `Name` = the same expression you wrote for `name`, repeated; `Role` = `"guardduty"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above. (`Project` and `Owner` come from the provider's `default_tags`.)

**Docs:** [aws_iam_role](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/iam_role)

#### 4. What the role may do (permissions policy)

**Block Type:** `data`
**Data Source Type:** `aws_iam_policy_document`
**Data Source Name:** `permissions`

Exactly seven statements, nothing more. Every statement has `effect` = `"Allow"`.

| Argument | Set To |
|---|---|
| `statement` (nested block) | seven blocks, one per row of the next table |

| # | `sid` | `actions` | `resources` (a one-item list) | `condition` |
|---|---|---|---|---|
| 1 | `"AllowManagedRuleToSendS3EventsToGuardDuty"` | `["events:PutRule", "events:DeleteRule", "events:PutTargets", "events:RemoveTargets"]` | the managed-rule ARN, see below | one nested block: `test` = `"StringLike"`, `variable` = `"events:ManagedBy"`, `values` = `["malware-protection-plan.guardduty.amazonaws.com"]` |
| 2 | `"AllowGuardDutyToMonitorEventBridgeManagedRule"` | `["events:DescribeRule", "events:ListTargetsByRule"]` | the managed-rule ARN | none |
| 3 | `"AllowPostScanTag"` | `["s3:PutObjectTagging", "s3:GetObjectTagging", "s3:PutObjectVersionTagging", "s3:GetObjectVersionTagging"]` | the `incoming_bucket_arn` variable followed by `/*` | none |
| 4 | `"AllowEnableS3EventBridgeEvents"` | `["s3:PutBucketNotification", "s3:GetBucketNotification"]` | the `incoming_bucket_arn` variable, as is | none |
| 5 | `"AllowPutValidationObject"` | `["s3:PutObject"]` | the `incoming_bucket_arn` variable followed by `/malware-protection-resource-validation-object` | none |
| 6 | `"AllowCheckBucketOwnership"` | `["s3:ListBucket"]` | the `incoming_bucket_arn` variable, as is | none |
| 7 | `"AllowMalwareScan"` | `["s3:GetObject", "s3:GetObjectVersion"]` | the `incoming_bucket_arn` variable followed by `/*` | none |

**The managed-rule ARN** (statements 1 and 2) is one string built from five parts: `arn:aws:events:`, the `region` of `data.aws_region.current`, a colon, the `account_id` of `data.aws_caller_identity.current`, and `:rule/DO-NOT-DELETE-AmazonGuardDutyMalwareProtectionS3*`. The `*` at the end is part of the value: GuardDuty adds a suffix to the rule's name. The finished string looks like `arn:aws:events:<region>:<account ID>:rule/DO-NOT-DELETE-AmazonGuardDutyMalwareProtectionS3*`, with a colon between the region and the account ID.

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [AWS's permissions template](https://docs.aws.amazon.com/guardduty/latest/ug/malware-protection-s3-iam-policy-prerequisite.html#attach-iam-policy-s3-malware-protection) · [Condition operators](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html)

What the seven statements do, in plain words:

- **1 and 2** let GuardDuty create and watch one EventBridge rule, named `DO-NOT-DELETE-AmazonGuardDutyMalwareProtectionS3...`, that listens for new files in the bucket. The `condition` on statement 1 limits those changes to rules that GuardDuty's malware service manages. Never delete that rule by hand.
- **4** lets GuardDuty turn on S3's event notifications for EventBridge on this bucket.
- **5** lets it write a small validation object to the bucket's root, which it uses to check the setup works. **6** lets it check who owns the bucket.
- **7** lets it read each file so it can scan it, and **3** lets it write the result tag.

The template gives statements 3 and 7 the whole bucket (`/*`), and so do you. The plan's `object_prefixes` in Part 2 is what limits scanning to `uploads/`. AWS's page also says to add an `s3:prefix` condition when you use an object prefix, but its own template shows none, so neither do we. Copy the template as written: tightening these statements is a stretch goal that has to be tested against the plan's status in a real account. AWS's page has an eighth statement for buckets encrypted with a KMS key. Ours use SSE-S3, so leave it out; SSE-KMS is a stretch goal.

For IAM roles, the `id` *is* the role's name, which is what `role` expects.

## Part 2: The protection plan (`modules/scanning/guardduty.tf`, new file)

#### 6. The plan

**Block Type:** `resource`
**Resource Type:** `aws_guardduty_malware_protection_plan`
**Resource Name:** `incoming`

| Argument | Set To |
|---|---|
| `role` | the `arn` of `aws_iam_role.guardduty` |
| `protected_resource` (nested block) | one block holding one `s3_bucket` block (next two rows) |
| `protected_resource` → `s3_bucket` → `bucket_name` | the `incoming_bucket_name` variable |
| `protected_resource` → `s3_bucket` → `object_prefixes` | `["uploads/"]` |
| `actions` (nested block) | one block holding one `tagging` block (next row) |
| `actions` → `tagging` → `status` | `"ENABLED"` |
| `tags` | `Name` = the `project_name` variable followed by `-incoming-scan`; `Role` = `"guardduty"`; `ManagedBy` = `"terraform"` |
| `depends_on` | a list holding `aws_iam_role_policy.guardduty`, written on one line |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_guardduty_malware_protection_plan](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/guardduty_malware_protection_plan) · [How Malware Protection for S3 works](https://docs.aws.amazon.com/guardduty/latest/ug/how-malware-protection-for-s3-gdu-works.html) · [depends_on](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on)

Read together: "use this role to scan the Incoming bucket, but only files whose key starts with `uploads/`, and tag each file with its result."

- **`object_prefixes`** limits the scan to keys that start with one of the listed prefixes (up to five). Lambda 1 puts every upload under `uploads/{upload_id}/`, so that prefix covers all of them, and nothing else in the bucket costs scan money.
- **Tagging** makes GuardDuty write a tag `GuardDutyMalwareScanStatus` onto each scanned file, set to the result (`NO_THREATS_FOUND`, `THREATS_FOUND`, and so on). It only tags files uploaded *after* tagging is on, which is why you set it now instead of later ([details](https://docs.aws.amazon.com/guardduty/latest/ug/how-malware-protection-for-s3-gdu-works.html#enable-optional-tagging-malware-protection-s3)).
- **`depends_on`** matters here. Terraform only waits for resources you reference, and the plan references the role but not the role's policy. Without it, Terraform may create the plan the moment the role exists, before the permissions are attached, and GuardDuty uses the role right away to set the plan up. The check matches this line as text, so write it exactly as `depends_on = [aws_iam_role_policy.guardduty]`, on one line.

## Done when (in your own AWS account)

These commands need the AWS CLI v2: `aws --version` should start with `aws-cli/2.`. If `aws guardduty` says it has no `get-malware-protection-plan` command, update the CLI. Run everything in this section in one terminal window: the later commands use variables the first ones set. Then, from the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
PLAN=$(terraform output -raw guardduty_plan_id)
BUCKET=$(terraform output -raw incoming_bucket_name)
T=$(mktemp -d)

# 1. Wait for the plan to be ACTIVE or ERROR (up to 5 minutes), then look at it
#    expect Status ACTIVE, Prefixes ["uploads/"], Tagging ENABLED, and no Reasons
for i in $(seq 30); do
  S=$(aws guardduty get-malware-protection-plan --malware-protection-plan-id "$PLAN" --query Status --output text)
  case "$S" in ACTIVE|ERROR) break ;; esac
  sleep 10
done
aws guardduty get-malware-protection-plan --malware-protection-plan-id "$PLAN" \
  --query '{Status: Status, Prefixes: ProtectedResource.S3Bucket.ObjectPrefixes, Tagging: Actions.Tagging.Status, Reasons: StatusReasons}'

# 2. Upload one file inside uploads/ and one outside it
echo "hello" > "$T/hello.txt"
aws s3 cp "$T/hello.txt" "s3://$BUCKET/uploads/c1-test/hello.txt"
aws s3 cp "$T/hello.txt" "s3://$BUCKET/outside/hello.txt"

# 3. Wait for the scan result tag on the first file (up to 5 minutes)
for i in $(seq 30); do
  N=$(aws s3api get-object-tagging --bucket "$BUCKET" --key uploads/c1-test/hello.txt \
    --query "length(TagSet[?Key=='GuardDutyMalwareScanStatus'])")
  [ "$N" = 1 ] && break
  sleep 10
done
aws s3api get-object-tagging --bucket "$BUCKET" --key uploads/c1-test/hello.txt

# 4. The file outside uploads/ must have no scan tag: expect {"TagSet": []}
aws s3api get-object-tagging --bucket "$BUCKET" --key outside/hello.txt

rm -r "$T"
```

Expected: (1) `"Status": "ACTIVE"` with the prefix and tagging values above and an empty `Reasons` (`[]` or `null`). Don't upload anything until it says `ACTIVE`: a file uploaded earlier is never scanned; (3) a tag set that includes `"Key": "GuardDutyMalwareScanStatus"` and `"Value": "NO_THREATS_FOUND"`; (4) an empty `TagSet`, which shows the plan scans only `uploads/`. Run step 4 after step 3 has found its tag, so the scanner has had time to tag the second file if it were going to.

Before `terraform destroy`, empty the bucket **including old versions**: Incoming is versioned, and `destroy` can't delete a bucket that still holds anything. This removes every version and delete marker (your test uploads are in there, so there is always something to remove):

```bash
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' --output json)"
terraform destroy
```

Things that commonly go wrong:

- **The plan's status is `WARNING` or `ERROR`, or `apply` fails while creating the plan**: read `StatusReasons` in step 1's output; each code is explained in [Troubleshooting Malware Protection for S3 status issues](https://docs.aws.amazon.com/guardduty/latest/ug/troubleshoot-s3-malware-protection.html). The usual cause is a mistake in the permissions document, so compare your seven statements with the table. IAM changes also take a few seconds to spread, so if everything matches, wait a minute and run `terraform apply` again.
- **No tag after 5 minutes**: check that step 1 says `ACTIVE`, that the key starts with exactly `uploads/`, and that you uploaded after the plan became active (files uploaded earlier are not scanned).
- **The file outside `uploads/` got a tag too**: `object_prefixes` is missing or wrong. Check the trailing slash.
- **`get-object-tagging` says `AccessDenied`**: your own AWS user needs `s3:GetObjectTagging` on the bucket; the pipeline's roles never use this command.

```bash
git add -A && git commit -m "chore(c1): add C1 to milestones.txt" && git push
```

Before you mark it ready, check GitHub once. `scripts/remote-check.sh` follows the run your last push started and prints the same summary, and it needs no new commit or push ([A1](A1.md#how-to-see-your-results) explains the output):

```bash
scripts/remote-check.sh
```

Paste the "Done when" output into your draft PR. The repo is squash-only, so the PR's title becomes the commit on `main`, and `--fill` named it after your first checkpoint. Retitle it to the whole milestone, then mark it ready (see A1's [Mark the pull request ready](A1.md#mark-the-pull-request-ready)):

```bash
gh pr edit --title "feat(c1): enable GuardDuty malware scanning on Incoming"
gh pr ready
```

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D c1-guardduty
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/c1-guardduty` ref.
