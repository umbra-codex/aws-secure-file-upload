## Goal

C1 made GuardDuty scan every file under `uploads/`. Each time it finishes one, it publishes a **scan result event** to EventBridge, and nothing is listening yet. In this milestone you connect that event to Lambda 2, the router that decides where each file goes (D builds it; its function already exists once D1 is merged). You build:

- **A rule** that catches every scan result.
- **A target** that sends each caught event to Lambda 2, with a short, explicit retry policy.
- **A dead-letter queue (DLQ)** that keeps any event EventBridge couldn't hand over, so a delivery failure is captured and can be replayed.
- **Two permissions** that make the delivery work: one for EventBridge to invoke Lambda 2, one for EventBridge to write into the DLQ.

Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't. The concepts, briefly:

- **EventBridge** is AWS's event router. Every AWS service that publishes events puts them on the **default event bus** in your account. A **rule** watches the bus for events that match an **event pattern**, and sends each match to its **targets**. Read [How EventBridge rules work](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rules.html) if the idea is new.
- **Delivery is asynchronous.** EventBridge hands the event to Lambda and moves on; it doesn't wait for your code to finish. That is why there are two different failure queues in this project, covered at the end of Part 3.

## Part 1: The rule (`modules/scanning/rule.tf`, new file)

#### 1. The scan-result rule

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_event_rule`
**Resource Name:** `scan_result`

| Argument | Set To |
|---|---|
| `name` | the `project_name` variable followed by `-scan-result` |
| `description` | a short sentence saying what the rule catches |
| `event_pattern` | `jsonencode` of an object with exactly two keys, see below |
| `tags` | `Name` = the same expression you wrote for `name`, repeated; `Role` = `"scan-rule"`; `ManagedBy` = `"terraform"` |

The two keys of the pattern:

| Key | Value |
|---|---|
| `source` | `["aws.guardduty"]` |
| `detail-type` | `["GuardDuty Malware Protection Object Scan Result"]` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_cloudwatch_event_rule](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_event_rule) · [Event patterns](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-event-patterns.html) · [GuardDuty's scan result event](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html#s3-object-scan-status-malware-protection-s3-ev) · [jsonencode](https://developer.hashicorp.com/terraform/language/functions/jsonencode)

An **event pattern** is a JSON document that looks like the events you want. A field matches when the event's value is one of the values in your list. Here is an abridged version of the event GuardDuty publishes when it finds malware (adapted from AWS's sample):

```json
{
  "detail-type": "GuardDuty Malware Protection Object Scan Result",
  "source": "aws.guardduty",
  "detail": {
    "scanStatus": "COMPLETED",
    "s3ObjectDetails": {
      "bucketName": "amzn-s3-demo-bucket",
      "objectKey": "uploads/0b7c.../photo.png",
      "versionId": "d41d8cd98f00b204e9800998eEXAMPLE"
    },
    "scanResultDetails": {
      "scanResultStatus": "THREATS_FOUND"
    }
  }
}
```

Your pattern keeps the first two fields and ignores the rest. The key `detail-type` has a hyphen; Terraform accepts that bare (`detail-type = [...]`) or quoted (`"detail-type" = [...]`), and `terraform fmt` leaves either alone. The pattern has no `scanResultStatus` on purpose: Lambda 2 has to see **every** result, clean or not, because it quarantines everything that isn't clean. The rule has no `event_bus_name`, so it watches the default bus, which is where GuardDuty publishes.

## Part 2: The dead-letter queue (`modules/scanning/dlq.tf`, new file)

An **SQS queue** is a holding area for messages. A **dead-letter queue** is a queue that collects messages that couldn't be delivered, so nothing is lost silently. EventBridge writes into yours only when it fails to deliver an event to Lambda 2. Read [Using dead-letter queues](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rule-dlq.html) for the full picture.

#### 2. The queue

**Block Type:** `resource`
**Resource Type:** `aws_sqs_queue`
**Resource Name:** `dlq`

| Argument | Set To |
|---|---|
| `name` | the `project_name` variable followed by `-scan-dlq` |
| `message_retention_seconds` | `1209600` |
| `sqs_managed_sse_enabled` | `true` |
| `tags` | `Name` = the same expression you wrote for `name`, repeated; `Role` = `"scan-dlq"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_sqs_queue](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/sqs_queue) · [Queue parameters, including message retention](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-queue-parameters.html) · [Encryption at rest](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-server-side-encryption.html)

`1209600` seconds is 14 days, the longest SQS allows. A queue keeps messages for four days by default; failed events need time to be noticed, fixed, and replayed, so you take the maximum. `sqs_managed_sse_enabled` encrypts the messages at rest. New queues usually have it on already; you set it explicitly so the intent is written down and the check can see it.

#### 3. Who may write to the queue (queue policy document)

**Block Type:** `data`
**Data Source Type:** `aws_iam_policy_document`
**Data Source Name:** `dlq`

| Argument | Set To |
|---|---|
| `statement` (nested block) | exactly one block with the rows below |
| `statement` → `sid` | `"AllowScanRuleToSendFailedEvents"` |
| `statement` → `effect` | `"Allow"` |
| `statement` → `actions` | `["sqs:SendMessage"]` |
| `statement` → `resources` | a list holding the `arn` of `aws_sqs_queue.dlq` |
| `statement` → `principals` (nested block) | one block: `type` = `"Service"`, `identifiers` = `["events.amazonaws.com"]` |
| `statement` → `condition` (nested block) | one block: `test` = `"ArnEquals"`, `variable` = `"aws:SourceArn"`, `values` = a list holding the `arn` of `aws_cloudwatch_event_rule.scan_result` |

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [AWS's example for a rule's DLQ](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rule-dlq.html#eb-dlq-perms)

This is a **resource-based policy**: a policy attached to the queue itself that says who may use it. Without it, EventBridge is not allowed to write, and a failed event vanishes without a trace. Terraform does not add it for you. The `condition` narrows the permission to events coming from your scan-result rule: other rules, in this account or any other, can't use your queue.

| Argument | Set To |
|---|---|
| `queue_url` | the `url` of `aws_sqs_queue.dlq` |
| `policy` | the `json` of `data.aws_iam_policy_document.dlq` |

**Tags:** not supported by this resource type.

**Docs:** [aws_sqs_queue_policy](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/sqs_queue_policy)

You wrote the rule first (Part 1) because this policy needs its ARN.

## Part 3: Delivery (`modules/scanning/target.tf`, new file)

#### 5. The target

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_event_target`
**Resource Name:** `router`

| Argument | Set To |
|---|---|
| `rule` | the `name` of `aws_cloudwatch_event_rule.scan_result` |
| `arn` | the `router_lambda_arn` variable |
| `retry_policy` (nested block) | one block with the two rows below |
| `retry_policy` → `maximum_retry_attempts` | `2` |
| `retry_policy` → `maximum_event_age_in_seconds` | `300` |
| `dead_letter_config` (nested block) | one block: `arn` = the `arn` of `aws_sqs_queue.dlq` |

**Tags:** not supported by this resource type.

**Docs:** [aws_cloudwatch_event_target](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_event_target) · [Retry policy](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-rule-retry-policy.html)

A **target** is what a rule does with a matched event. Here it invokes Lambda 2. When delivery fails for a reason that might pass (for example, Lambda is throttling requests), EventBridge retries. By default it keeps trying for 24 hours and up to 185 times, which would hide a broken pipeline for a day. Your policy gives up after 2 retries or 5 minutes, whichever comes first, and then sends the event to the DLQ, so a failure shows up in minutes. (Some failures, like a missing permission, skip the retries and go straight to the DLQ.)

**What the DLQ does not catch.** It holds events EventBridge could not *deliver*: a missing permission, a deleted function, throttling. Once Lambda accepts an event, a bug or crash inside Lambda 2 is Lambda's to retry, not EventBridge's, and D builds a separate failure queue (`router-failures`) for that. The two queues cover different failures, and the project needs both.

#### 6. Let EventBridge invoke the function

**Block Type:** `resource`
**Resource Type:** `aws_lambda_permission`
**Resource Name:** `scan_rule`

| Argument | Set To |
|---|---|
| `statement_id` | `"AllowScanRule"` |
| `action` | `"lambda:InvokeFunction"` |
| `function_name` | the `router_lambda_arn` variable |
| `principal` | `"events.amazonaws.com"` |
| `source_arn` | the `arn` of `aws_cloudwatch_event_rule.scan_result` |

**Tags:** not supported by this resource type.

**Docs:** [aws_lambda_permission](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/lambda_permission) · [Resource-based policies for Lambda](https://docs.aws.amazon.com/lambda/latest/dg/access-control-resource-based.html)

A Lambda function can be invoked only by callers it has granted permission, and this is that grant: "the EventBridge service may invoke this function, but only on behalf of this rule." Note that `source_arn` is the **rule's** ARN, not the function's. The target in section 5 doesn't create this for you. The fixed `statement_id` lets "Done when" remove the permission by name to test the DLQ. The permission lives in your module, next to the rule, even though the function belongs to D.

## Done when (in your own AWS account)

Run the commands one at a time. A command that runs over several lines (ending in `\`, or a `{ ... }` block) goes in whole. `apply` and `destroy` each stop and ask you to type `yes`, and `destroy` is finished when it prints `Destroy complete!`.

These commands need the AWS CLI v2: `aws --version` should start with `aws-cli/2.` (version 1 has no `aws logs tail`). Your `apply` needs C1 and D1 in `main`, because it deploys the router function this rule calls. Run everything in this section in one terminal window: the later commands use variables the first ones set. Then, from the repo root:

```bash
terraform init -backend-config=backend.hcl
mkdir -p .evidence
exec > >(tee .evidence/c2-done.txt) 2>&1
set -x
terraform apply
BUCKET=$(terraform output -raw incoming_bucket_name)
ROUTER=$(terraform output -raw router_function_name)
DLQ=$(terraform output -raw scan_dlq_name)
T=$(mktemp -d)
echo "hello" > "$T/hello.txt"

# 1. The normal path: upload a file, then wait for Lambda 2's log to mention it (up to 5 minutes)
ID=c2-$(date +%s)
aws s3 cp "$T/hello.txt" "s3://$BUCKET/uploads/$ID/hello.txt"
for i in $(seq 30); do
  aws logs tail "/aws/lambda/$ROUTER" --since 15m | grep -q "$ID" && break
  sleep 10
done
aws logs tail "/aws/lambda/$ROUTER" --since 15m | grep "$ID"

# 2. The failure path: take away EventBridge's permission, upload again, wait for the DLQ
aws lambda remove-permission --function-name "$ROUTER" --statement-id AllowScanRule
sleep 20
ID2=c2-fail-$(date +%s)
aws s3 cp "$T/hello.txt" "s3://$BUCKET/uploads/$ID2/hello.txt"
DLQ_URL=$(aws sqs get-queue-url --queue-name "$DLQ" --query QueueUrl --output text)
for i in $(seq 30); do
  N=$(aws sqs get-queue-attributes --queue-url "$DLQ_URL" --attribute-names ApproximateNumberOfMessages \
    --query Attributes.ApproximateNumberOfMessages --output text)
  [ "$N" != 0 ] && break
  sleep 10
done
echo "messages in the DLQ: $N"
aws sqs receive-message --queue-url "$DLQ_URL" --message-attribute-names All --visibility-timeout 0 \
  --query 'Messages[0].MessageAttributes'
aws sqs purge-queue --queue-url "$DLQ_URL"   # empty the DLQ again; a purge takes up to a minute

# 3. Put the permission back: expect "1 to add" (the Lambda permission)
terraform apply

rm -r "$T"
```

Expected: (1) a log line from Lambda 2 that contains `uploads/c2-.../hello.txt` (D1 logs the event it receives), proving the scan result reached the function; (2) `messages in the DLQ: 1` (or more), and message attributes such as `RULE_ARN`, `TARGET_ARN`, `ERROR_CODE`, and `ERROR_MESSAGE` that name the missing permission; (3) a plan that adds the Lambda permission back. The `purge-queue` line empties the DLQ so nothing stale is left for the next milestone's alarm. Step 2 is a real outage, on purpose: with no permission, EventBridge can't invoke the function, and your queue policy is what lets it save the event instead. `terraform apply` repairs the **drift**, the difference between your code and what's now in AWS.

Before `terraform destroy`, empty the Incoming bucket **including old versions**: it is versioned, and `destroy` can't delete a bucket that still holds anything. This removes every version and delete marker (your test uploads are in there, so there is always something to remove):

```bash
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' --output json)"
terraform destroy
```

Things that commonly go wrong:

- **No log line in step 1**: the rule takes up to a minute to start matching after `apply`, so upload again. Then check that C1's plan is still `ACTIVE`, and that the rule has its target: `aws events list-rule-names-by-target --target-arn "$(aws lambda get-function --function-name "$ROUTER" --query Configuration.FunctionArn --output text)"` should print your scan-result rule's name.
- **The log line never mentions the file**: D1's function logs the whole event, so look at the raw log (`aws logs tail "/aws/lambda/$ROUTER" --since 15m`). If the invocation is there but the key is not, the event pattern or D1's logging is the place to look.
- **`remove-permission` says `ResourceNotFoundException`**: the permission is already gone, or its `statement_id` is not exactly `AllowScanRule`.
- **The DLQ stays empty after 5 minutes although the permission is gone**: the queue policy is the usual cause. Print it with `aws sqs get-queue-attributes --queue-url "$DLQ_URL" --attribute-names Policy` and compare it with section 3, especially the `aws:SourceArn`. Without a working policy EventBridge can't write, and the event is lost.
- **`receive-message` prints `null`**: a message may be invisible for a moment after another read. Run it again, or wait 30 seconds.

```bash
{ cat .github/pull_request_template.md; echo '```'; sed -E -e '/^\+ (tofu|terraform) destroy/,$d' -e 's/[[:alnum:]._%+-]+@[[:alnum:].-]+\.[[:alpha:]]{2,}/<email>/g' .evidence/c2-done.txt; echo '```'; } > .evidence/c2-pr.md
gh pr edit --body-file .evidence/c2-pr.md
set +x
exec > /dev/tty 2>&1
```

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D c2-scan-rule
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/c2-scan-rule` ref.
