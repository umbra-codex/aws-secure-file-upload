## Goal

The pipeline scans every upload and quarantines anything suspicious, but nobody knows unless they look. In this milestone you make it tell the team. You build:

- **An alert rule** that catches two kinds of GuardDuty events: a scan that **found malware**, and a **scanner error** (GuardDuty reporting that the protection plan itself is broken, for example because someone removed a permission).
- **An SNS topic** with an **email subscription** to the `alert_email` address, so those events arrive in an inbox.
- **A topic policy** that lets only that rule, and later the DLQ alarm, publish to the topic.
- **A CloudWatch alarm** that goes off when C2's dead-letter queue holds any message, meaning a scan result could not be delivered to Lambda 2, and publishes to the same topic when it does, so the same address is emailed.

Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't. The new idea is **SNS** (Simple Notification Service): you publish a message to a **topic**, and SNS forwards it to every **subscription** on it (an email address, here). Read [What is Amazon SNS?](https://docs.aws.amazon.com/sns/latest/dg/welcome.html) if it's new. The rest follows C2's pattern: a rule, a target, and a resource policy that lets EventBridge use the target.

## Part 1: The alert rule (`modules/scanning/alert_rule.tf`, new file)

#### 1. The alert rule

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_event_rule`
**Resource Name:** `alerts`

| Argument | Set To |
|---|---|
| `name` | the `project_name` variable followed by `-alerts` |
| `description` | a short sentence saying what the rule catches |
| `event_pattern` | `jsonencode` of an object with three keys, see below |
| `tags` | `Name` = the same expression you wrote for `name`, repeated; `Role` = `"alerts"`; `ManagedBy` = `"terraform"` |

The three keys of the pattern:

| Key | Value |
|---|---|
| `source` | `["aws.guardduty"]` |
| `detail-type` | a list of two strings: `"GuardDuty Malware Protection Object Scan Result"` and `"GuardDuty Malware Protection Resource Status Error"` |
| `detail` | an object with exactly one key, `"$or"`, whose value is a list of two objects (next table) |

The two objects inside `"$or"`:

| # | Object |
|---|---|
| 1 | one key, `scanResultDetails`, whose value is an object with one key, `scanResultStatus` = `["THREATS_FOUND"]` |
| 2 | one key, `resourceStatus` = `["ERROR"]` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_cloudwatch_event_rule](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_event_rule) · [Event patterns](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-event-patterns.html) · [`$or` matching](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-create-pattern-operators.html#eb-filtering-complex-example-or) · [GuardDuty's event samples](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html)

**Why the pattern has an `$or`.** EventBridge requires **every** field in a pattern to match. The two events you want look different:

```json
{ "detail-type": "GuardDuty Malware Protection Object Scan Result",
  "detail": { "scanResultDetails": { "scanResultStatus": "THREATS_FOUND" } } }

{ "detail-type": "GuardDuty Malware Protection Resource Status Error",
  "detail": { "resourceStatus": "ERROR" } }
```

The scanner-error event has a different `detail-type` and no `scanResultDetails` at all, so one flat pattern can match one event or the other but never both. `"$or"` says "match if **either** of these conditions holds." Read the pattern as: from GuardDuty, and either a scan-result event or a status-error event, and (the scan found threats, or the status is `ERROR`). Because the list under `detail-type` is also an "either", a scan-result event with a clean result matches the `detail-type` but neither `"$or"` condition, so it stays quiet.

Leave `event_bus_name` unset, as in C2 (the check reads it). Write `"$or"` as a quoted key, `"$or" = [...]`: a `$` isn't allowed in a bare Terraform key. (`detail-type` may be bare or quoted, as in C2.) Only `THREATS_FOUND` raises an alert. Other outcomes (`UNSUPPORTED`, `ACCESS_DENIED`, `FAILED`) quarantine the file quietly, as Lambda 2's routing table says.

## Part 4: The dead-letter queue alarm (`modules/scanning/alarm.tf`, new file, and a change to `alerts_topic.tf`)

A **CloudWatch alarm** watches one metric and changes state when it crosses a threshold: `OK`, `ALARM`, or `INSUFFICIENT_DATA`. SQS publishes a metric, `ApproximateNumberOfMessagesVisible`, for every queue: the number of messages waiting in it. C2's DLQ should always be empty, so any message at all is a delivery failure that needs a look.

#### 7. The alarm

**Block Type:** `resource`
**Resource Type:** `aws_cloudwatch_metric_alarm`
**Resource Name:** `dlq_not_empty`

| Argument | Set To |
|---|---|
| `alarm_name` | the `project_name` variable followed by `-scan-dlq-not-empty` |
| `alarm_description` | a short sentence saying what it means |
| `namespace` | `"AWS/SQS"` |
| `metric_name` | `"ApproximateNumberOfMessagesVisible"` |
| `dimensions` | a map with one entry: `QueueName` = the `name` of `aws_sqs_queue.dlq` |
| `statistic` | `"Maximum"` |
| `period` | `60` |
| `evaluation_periods` | `1` |
| `threshold` | `0` |
| `comparison_operator` | `"GreaterThanThreshold"` |
| `treat_missing_data` | `"notBreaching"` |
| `alarm_actions` | a list holding the `arn` of `aws_sns_topic.alerts` |
| `tags` | `Name` = the same expression you wrote for `alarm_name`, repeated; `Role` = `"observability"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_cloudwatch_metric_alarm](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/cloudwatch_metric_alarm) · [SQS metrics](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-available-cloudwatch-metrics.html) · [How alarms evaluate](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation.html)

Read together: "look at the most messages that were waiting at any moment in each 60-second window, and go to `ALARM` if that is more than zero." `Maximum` catches a message even if it was read again within the minute. `notBreaching` treats missing data as healthy, because a queue nobody has written to has no data points to report.

An **alarm action** is what the alarm does when it changes state. Here, when it moves into `ALARM`, CloudWatch publishes a message to your alerts topic, and SNS forwards it to the email you confirmed in Part 2. Only `alarm_actions` is set. There is no `ok_actions`, so you get one email when the queue fills, not one when it drains. The action alone is not enough, which is why the next section exists.

#### 8. Let the alarm publish (edit the topic policy document in `alerts_topic.tf`)

Go back to `data.aws_iam_policy_document.alerts_topic` from section 3 and add a **second** `statement` block inside that same `data` block, after the existing one, so the document holds exactly two:

| Argument | Set To |
|---|---|
| `statement` → `sid` | `"AllowDlqAlarmToPublish"` |
| `statement` → `effect` | `"Allow"` |
| `statement` → `actions` | `["sns:Publish"]` |
| `statement` → `resources` | a list holding the `arn` of `aws_sns_topic.alerts` |
| `statement` → `principals` (nested block) | one block: `type` = `"Service"`, `identifiers` = `["cloudwatch.amazonaws.com"]` |
| `statement` → `condition` (nested block) | one block: `test` = `"ArnEquals"`, `variable` = `"aws:SourceArn"`, `values` = a list holding the `arn` of `aws_cloudwatch_metric_alarm.dlq_not_empty` |

**Tags:** not supported (data sources don't create anything).

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [Example cases for SNS access control](https://docs.aws.amazon.com/sns/latest/dg/sns-access-policy-use-cases.html)

Section 3's policy replaced the topic's default one, and it lets in only EventBridge. When the alarm fires, the caller is the CloudWatch service, so without this statement the publish is refused and the alarm moves to `ALARM` without sending you anything. As in section 3, the `condition` limits the grant to one source, here your DLQ alarm. (AWS also suggests an `aws:SourceAccount` condition; the alarm's ARN already contains your account ID, so the ARN match is enough.) (This statement refers to the alarm, and the alarm refers to the topic; Terraform handles that because the alarm needs only the topic, not the policy.)

**2. Test the alert pattern against four sample events**, without sending anything. This covers the scanner-error branch too, which can't be triggered on demand: GuardDuty emits it only when a plan breaks.

```bash
PATTERN=$(aws events describe-rule --name "$RULE" --query EventPattern --output text)
try() { aws events test-event-pattern --event-pattern "$PATTERN" --event "$1" --query Result --output text; }
EV='"id":"1","account":"111122223333","source":"aws.guardduty","time":"2024-02-28T01:01:01Z","region":"us-east-1","resources":[]'
echo "threat found:     $(try "{$EV,\"detail-type\":\"GuardDuty Malware Protection Object Scan Result\",\"detail\":{\"scanResultDetails\":{\"scanResultStatus\":\"THREATS_FOUND\"}}}")"
echo "no threats:       $(try "{$EV,\"detail-type\":\"GuardDuty Malware Protection Object Scan Result\",\"detail\":{\"scanResultDetails\":{\"scanResultStatus\":\"NO_THREATS_FOUND\"}}}")"
echo "scanner error:    $(try "{$EV,\"detail-type\":\"GuardDuty Malware Protection Resource Status Error\",\"detail\":{\"resourceStatus\":\"ERROR\"}}")"

```

Expected: `True`, `False`, `True`, `False`, in that order.

**3. Upload the EICAR test file and wait for the email.** EICAR is a harmless 68-character text file that every virus scanner reports as malware, made for exactly this test. The first command builds it from two pieces, so this document itself isn't flagged by antivirus software. If your own antivirus deletes the file as you create it, that's it working: pause its real-time protection for a minute, or create the file in a folder it ignores.

```bash
printf '%s%s' 'X5O!P%@AP[4\PZX54(P^)7CC)7}$EICAR-STANDARD-' 'ANTIVIRUS-TEST-FILE!$H+H*' > "$T/eicar.txt"
aws s3 cp "$T/eicar.txt" "s3://$BUCKET/uploads/c3-eicar/eicar.txt"
for i in $(seq 30); do
  N=$(aws s3api get-object-tagging --bucket "$BUCKET" --key uploads/c3-eicar/eicar.txt \
    --query "length(TagSet[?Key=='GuardDutyMalwareScanStatus'])")
  [ "$N" = 1 ] && break
  sleep 10
done
aws s3api get-object-tagging --bucket "$BUCKET" --key uploads/c3-eicar/eicar.txt
```

Expected: a tag set that includes `"Key": "GuardDutyMalwareScanStatus"` with `"Value": "THREATS_FOUND"`, and within a minute or two an email from AWS Notifications whose body is JSON containing `"scanResultStatus": "THREATS_FOUND"` and `uploads/c3-eicar/eicar.txt`. If no email arrives, see the list below.

**4. Break the pipeline on purpose and watch the alarm.** The alarm is named after the queue: `<project_name>-scan-dlq-not-empty`. First check that it is quiet. Expect `OK` or `INSUFFICIENT_DATA`; if it already says `ALARM`, an earlier failed delivery is still sitting in the DLQ, so purge it (`aws sqs purge-queue --queue-url "$(aws sqs get-queue-url --queue-name "$DLQ" --query QueueUrl --output text)"`), wait two minutes for `OK`, and start again.

```bash
ALARM_NAME="${DLQ}-not-empty"
aws cloudwatch describe-alarms --alarm-names "$ALARM_NAME" --query 'MetricAlarms[0].StateValue' --output text
```

Now remove EventBridge's permission to call Lambda 2 (the same trick as C2's "Done when"), upload a clean file, and wait for the alarm:

```bash
aws lambda remove-permission --function-name "$ROUTER" --statement-id AllowScanRule
sleep 20
echo "hello" > "$T/hello.txt"
aws s3 cp "$T/hello.txt" "s3://$BUCKET/uploads/c3-fail/hello.txt"
for i in $(seq 30); do
  A=$(aws cloudwatch describe-alarms --alarm-names "$ALARM_NAME" --query 'MetricAlarms[0].StateValue' --output text)
  [ "$A" = ALARM ] && break
  [ "$A" = None ] && { echo "no alarm named $ALARM_NAME"; break; }
  sleep 20
done
echo "alarm state: $A"
```

Expected: `alarm state: ALARM` within about 5 minutes, and a minute or two later a new email (check its time) at the address you confirmed in step 1, with a subject that starts with `ALARM:` and names `<project_name>-scan-dlq-not-empty`. Then repair the drift. Expect a plan with "1 to add" (the Lambda permission):

```bash
terraform apply
rm -r "$T"
```

Before `terraform destroy`, empty the Incoming bucket **including old versions**: it is versioned, and `destroy` can't delete a bucket that still holds anything. This removes every version and delete marker (your test uploads are in there, so there is always something to remove):

```bash
aws s3api delete-objects --bucket "$BUCKET" --delete "$(aws s3api list-object-versions --bucket "$BUCKET" \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' --output json)"
terraform destroy
```

Things that commonly go wrong:

- **Step 1 shows `PendingConfirmation`**: you haven't clicked the link yet. Until you do, SNS delivers nothing to that address.
- **Step 2 prints something other than `True`, `False`, `True`, `False`**: the pattern in `alert_rule.tf` doesn't match the table in section 1. Print it with `echo "$PATTERN"`. A wrong `detail-type` string, a missing `"$or"`, or `THREATS_FOUND` spelled differently are the usual causes.
- **The tag is `THREATS_FOUND` but no email arrives**: check, in order, that step 1 is confirmed, the spam folder, and the topic policy's `aws:SourceArn`, which must be the **alert** rule's ARN. Also look at the rule's `FailedInvocations` metric under CloudWatch > Metrics > Events: a non-zero value means EventBridge could not publish, usually because of the topic policy.
- **No scan tag at all**: C1's plan isn't `ACTIVE`, or you uploaded before it was. See C1's "Done when".
- **The alarm reaches `ALARM` but no email arrives**: confirm step 1 said a real subscription ARN, and check the spam folder. Then list what CloudWatch tried: `aws cloudwatch describe-alarm-history --alarm-name "$ALARM_NAME" --history-item-type Action`. A failed action shows up there, and the usual cause is a missing or wrong second statement in the topic policy (section 8: the principal is `cloudwatch.amazonaws.com`, and the `aws:SourceArn` is the **alarm's** arn).
- **The alarm never reaches `ALARM`**: confirm `remove-permission` worked (it prints nothing on success), then check the queue: `aws sqs get-queue-attributes --queue-url "$(aws sqs get-queue-url --queue-name "$DLQ" --query QueueUrl --output text)" --attribute-names ApproximateNumberOfMessages`. A message that is there but no alarm means the alarm's dimension doesn't name this queue.

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D c3-alerts
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/c3-alerts` ref.
