## Goal

Every scan result ends up at Lambda 2, the **router**. It decides where each file goes, Approved or Quarantine, and records the outcome. D builds it in four milestones. This one builds only the function and its role, with code that does nothing but log the event it receives. That is already enough to unblock two other portions: C2 needs this function's ARN to aim the scan-result rule at, and A3's Quarantine policy needs the role's ARN.

In this milestone you build:

- **A Lambda function** (Python) that logs every event it receives. D2 teaches it to route.
- **An IAM role** that lets the function write its own logs, and nothing else. Permissions arrive together with the code that needs them: D2 adds access to the buckets, the table, and the failure queue.
- **A log group** that keeps 14 days of logs.

Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't. Skim B1's brief too: the pattern is the same (code, log group, role, function), with a different job.

**Why log the whole event first.** A real event is the best documentation there is. Before you write code that depends on its shape, you let it show you the shape. The "Done when" at the end invokes the function with AWS's sample event and finds it in the log.

## Part 1: The function's code (`modules/processing/src/handler.py`)

The code lives inside the module, in a `src` folder, so the module carries everything it needs. Create the folder and the file.

#### 1. What the handler must do

Write one function, `def handler(event, context):`, written exactly like that (the check matches the line). Lambda calls it with the event as a Python dictionary. It does this:

| Step | Behavior |
|---|---|
| 1 | At the top of the file, `import logging`, then create a logger: `logger = logging.getLogger()`. |
| 2 | First line of the function body: `logger.info("scan result received", extra={"scan_event": event})`. Write it exactly like that (the check matches it). |
| 3 | Return `{"logged": True}`. |

When GuardDuty finishes scanning a file, the event that reaches your function looks like this (abridged from AWS's sample):

```json
{
  "detail-type": "GuardDuty Malware Protection Object Scan Result",
  "source": "aws.guardduty",
  "detail": {
    "scanStatus": "COMPLETED",
    "resourceType": "S3_OBJECT",
    "s3ObjectDetails": {
      "bucketName": "amzn-s3-demo-bucket",
      "objectKey": "uploads/0b7c.../photo.png",
      "versionId": "d41d8cd98f00b204e9800998eEXAMPLE",
      "s3Throttled": false
    },
    "scanResultDetails": {
      "scanResultStatus": "NO_THREATS_FOUND",
      "threats": null,
      "statusReasons": null
    }
  }
}
```

Three fields matter from D2 on: `detail.s3ObjectDetails.objectKey` and `detail.s3ObjectDetails.versionId` say which file and which version was scanned, and `detail.scanResultDetails.scanResultStatus` is GuardDuty's verdict. For now you only log them.

**Why `extra`.** In Part 4 you switch the function to JSON logs. With JSON logs, every key in `extra` becomes a field of the log line, so the whole event becomes one searchable field named `scan_event`. This is the same trick B1 uses for `upload_id`.

**Keep this line.** D1's check runs again on every later milestone, so the `scan_event` line has to stay in the handler through D4. Leave it as the first line of the function and add your own code below it. The event holds names and IDs, never file contents, so logging all of it is safe.

**The return value only matters to you.** EventBridge calls the function and moves on without waiting for an answer (C2 explains why), so nobody reads what you return. Your own test invokes do.

**Tags:** not applicable (this is code, not a Terraform block).

**Docs:** [Logging in Python Lambda functions](https://docs.aws.amazon.com/lambda/latest/dg/python-logging.html) · [Logging extra fields in JSON](https://docs.aws.amazon.com/lambda/latest/dg/python-logging.html#python-logging-extra) · [GuardDuty's scan result event](https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html#s3-object-scan-status-malware-protection-s3-ev)

**Block Type:** `resource`
**Resource Type:** `aws_lambda_function`
**Resource Name:** `router`

| Argument | Set To |
|---|---|
| `function_name` | the `project_name` variable followed by `-router` |
| `role` | the `arn` of `aws_iam_role.router` |
| `runtime` | `"python3.13"` |

| `environment` → `TABLE_NAME` | the `table_name` variable |
| `environment` → `INCOMING_BUCKET` | the `incoming_bucket_name` variable |
| `environment` → `APPROVED_BUCKET` | the `approved_bucket_name` variable |
| `environment` → `QUARANTINE_BUCKET` | the `quarantine_bucket_name` variable |
| `environment` → `ALLOWED_TYPES` | the `allowed_types` variable joined into one string with commas. Use the `join` function. |
| `environment` → `MAX_SIZE_MB` | the `max_size_mb` variable |
| `logging_config` (nested block) | one block with the three rows below |
| `logging_config` → `log_format` | `"JSON"` |
| `logging_config` → `application_log_level` | `"INFO"` |
| `logging_config` → `log_group` | the `name` of `aws_cloudwatch_log_group.router` |
| `tags` | `Name` = the same expression you wrote for `function_name`, repeated; `Role` = `"router"`; `ManagedBy` = `"terraform"` |

**Tags:** yes, through the `tags` argument above.

**Docs:** [aws_lambda_function](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/lambda_function) · [join function](https://developer.hashicorp.com/terraform/language/functions/join) · [Lambda log groups and their permissions](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs-loggroups.html)

Three choices to understand:

- **`timeout` of 30 seconds.** Lambda 2 makes a handful of AWS calls per event. 30 seconds is far more than it needs, and it is the ceiling that stops a stuck call from running (and billing) for long.
- **`memory_size` of 512 on purpose.** Lambda gives a function CPU in proportion to its memory, so too little memory makes it slow. 512 is a safe place to start. D4 reads the real numbers from your logs and lowers it, which is the cheapest saving in the project.
- **Six environment variables, though D1's code reads none of them.** D2 and D3 read them. Setting all six now means those milestones change only code, never the function's configuration.

Environment variables are always strings, which is why the list has to be joined, and why the code later converts `MAX_SIZE_MB` back to a number. `logging_config` does two jobs: `log_format = "JSON"` makes Lambda write every `logger` call as one JSON object (so `extra` becomes fields), and `log_group` sends the logs to the group from Part 2. Because it references that group, Terraform also knows to create the group first, so no `depends_on` is needed.

## Done when (in your own AWS account)

These commands need the AWS CLI v2: `aws --version` should start with `aws-cli/2.` (version 1 has no `aws logs tail`). Run everything in this section in one terminal window: the later commands use variables the first ones set. From the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
ROUTER=$(terraform output -raw router_function_name)
T=$(mktemp -d)

# A scan-result event shaped like GuardDuty's (AWS's sample, with a test key)
cat > "$T/event.json" <<'EOF'
{
  "detail-type": "GuardDuty Malware Protection Object Scan Result",
  "source": "aws.guardduty",
  "detail": {
    "scanStatus": "COMPLETED",
    "resourceType": "S3_OBJECT",
    "s3ObjectDetails": {
      "bucketName": "amzn-s3-demo-bucket",
      "objectKey": "uploads/d1-test/cat.png",
      "versionId": "d41d8cd98f00b204e9800998eEXAMPLE",
      "s3Throttled": false
    },
    "scanResultDetails": {
      "scanResultStatus": "NO_THREATS_FOUND",
      "threats": null,
      "statusReasons": null
    }
  }
}
EOF

# Invoke the function with it: expect StatusCode 200 and no FunctionError
aws lambda invoke --function-name "$ROUTER" --payload "fileb://$T/event.json" "$T/out.json" \
  --query '[StatusCode,FunctionError]' --output text
cat "$T/out.json"; echo

# Wait for the log line (up to 1 minute), then print it
for i in $(seq 12); do
  aws logs tail "/aws/lambda/$ROUTER" --since 10m | grep -q scan_event && break
  sleep 5
done
aws logs tail "/aws/lambda/$ROUTER" --since 10m | grep scan_event

rm -r "$T"
terraform destroy
```

Expected: (1) `200` and `None` on one line, then `{"logged": true}`; (2) one JSON log line with `"message": "scan result received"` and a `scan_event` field that holds the whole event, including `uploads/d1-test/cat.png`. `fileb://` makes the CLI send the file as-is; with the plain `file://` form, CLI v2 would expect base64 text instead.

Nothing in this milestone touches a bucket, so `terraform destroy` has nothing to empty first.

Things that commonly go wrong:

- **`ResourceNotFoundException` ("Function not found")**: `apply` didn't finish, or `ROUTER` is empty because you opened a new terminal. Run `echo "$ROUTER"`.
- **`FunctionError` prints `Unhandled`**: the handler crashed. `cat "$T/out.json"` shows the error; the usual causes are a typo in `handler` (it must be `handler.handler`), a syntax error in the file, or a `NameError` because the file doesn't start with `import logging`.
- **No log line after a minute**: check that `log_group` in `logging_config` names the group from Part 2. If the group exists but stays empty, the role's `WriteLogs` resource is probably missing the trailing `:*`.
- **The log line has no `scan_event` field**: the function is still on plain-text logging. Check `log_format = "JSON"`, and that your line passes `extra={"scan_event": event}`.
- **`apply` fails with `The role defined for the function cannot be assumed by Lambda`**: the new role hasn't spread through IAM yet. Wait a few seconds and run `terraform apply` again.

Paste the "Done when" output into your draft PR. The repo is squash-only, so the PR's title becomes the commit on `main`, and `--fill` named it after your first checkpoint. Retitle it to the whole milestone, then mark it ready (see A1's [Mark the pull request ready](A1.md#mark-the-pull-request-ready)):


## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -D d1-router-lambda
git fetch --prune
```

`-D` rather than `-d` because this repo is squash-only: the branch's commits are never in `main` as themselves, so `git branch -d` refuses. The remote branch is already gone — `delete_branch_on_merge` removes it at merge — so `git fetch --prune` only clears the stale `origin/d1-router-lambda` ref.
