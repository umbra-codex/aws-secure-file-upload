## Goal

D1 gave you a router that logs what it receives. In this milestone it starts doing its job: for every scan result it moves the file to the right bucket and records the outcome in the uploads table. It is also the most security-sensitive code in the project, so read the rules below slowly. You build:

- **The routing code.** A clean file goes to Approved. Every other verdict goes to Quarantine. The file is copied by the exact version GuardDuty scanned, and the DynamoDB row is updated only if it is still `PENDING`.
- **The data permissions.** A second policy that gives the role exactly what the code needs: read and delete in Incoming, write in Approved and Quarantine, read and update one table, and send to one queue.
- **A failure queue** and an **on-failure destination**, so an event that Lambda 2 can't process is kept instead of lost.
- **`scripts/redrive.sh`**, which sends every kept event back to Lambda 2 once you have fixed the cause.

Read A1's [How to read the blocks](A1.md#how-to-read-the-blocks) if you haven't. The concepts, briefly:

- **A version.** Incoming is versioned: every upload to the same key creates a new **version** with its own `versionId`, and the old ones stay. GuardDuty's event names the version it scanned. Lambda 2 only ever touches that version.
- **Asynchronous invocation.** EventBridge hands the event to Lambda and moves on. If your code raises an error, Lambda retries it (you set it to once), and then either drops the event or, with an **on-failure destination**, sends a record of it to somewhere you choose. Read [Capturing records of Lambda asynchronous invocations](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async-retain-records.html) for the full picture.

## Part 1: The routing code (`modules/processing/src/handler.py`)

#### 1. What the handler must do

Keep `def handler(event, context):` and D1's logging line. The handler does this, in this order:

| Step | Behavior |
|---|---|
| 1 | At the top of the file, `import os` and `import boto3` (D1 already imported `logging`). Then read four settings from environment variables (`os.environ`), once: `TABLE_NAME`, `INCOMING_BUCKET`, `APPROVED_BUCKET`, `QUARANTINE_BUCKET`. Never hardcode them. Create the S3 client (`boto3.client("s3")`) and the table (`boto3.resource("dynamodb").Table(TABLE_NAME)`) there too, once. |
| 2 | Keep D1's line `logger.info("scan result received", extra={"scan_event": event})` as the first line of the function. |
| 3 | Read the scanned file from the event: `event["detail"]["s3ObjectDetails"]` holds `objectKey` and `versionId`, and `event["detail"]["scanResultDetails"]["scanResultStatus"]` is the verdict. |
| 4 | `upload_id` is the second segment of the object key: `objectKey.split("/")[1]`. Log a second line that carries it, for example `logger.info("scan result parsed", extra={"upload_id": upload_id, "scan_status": scan_status, "version_id": version_id})`. The check matches `extra={"upload_id":` with `upload_id` as the first key. |
| 5 | Read the upload's row: `TABLE.get_item(Key={"upload_id": upload_id})["Item"]`. (A missing row is D4's job; for now it raises.) |
| 6 | Rebuild the key as an f-string that starts `uploads/{upload_id}/` and ends with the row's `filename`. |
| 7 | Decide where the file goes (the routing table below). The destination is a bucket name, and a quarantined file also gets a `reason`. |
| 8 | Copy the scanned version into the destination bucket, under the same key, with `copy_object`. `CopySource` is a dictionary with `Bucket`, `Key` and `VersionId` (see "Copy by version"). |
| 9 | Record the outcome with `update_item`, conditionally (see "The conditional update"). |
| 10 | Delete the scanned version from Incoming with `delete_object`, passing its `VersionId`. |
| 11 | Log it on one line, for example `logger.info("scanned version moved", extra={"upload_id": upload_id, "destination": destination, "reason": reason})`, and return a dictionary with `destination` and `reason`. |

Don't catch errors in this milestone. If a call fails, let the exception escape: Lambda retries once and then sends the event to the failure queue you build in Part 2. D4 adds the few cases where catching is right.

**The routing table.** Every outcome except one goes to Quarantine:

| `scanResultStatus` | Meaning | Destination | `reason` |
|---|---|---|---|
| `NO_THREATS_FOUND` | Clean | Approved | none |
| `THREATS_FOUND` | Malware | Quarantine | `THREATS_FOUND` |
| `UNSUPPORTED` | Skipped, for example a password-protected file | Quarantine | `UNSUPPORTED` |
| `ACCESS_DENIED` | Skipped, for example an SSE-C encrypted file | Quarantine | `ACCESS_DENIED` |
| `FAILED` | The scan itself failed | Quarantine | `FAILED` |

Write it so that `NO_THREATS_FOUND` is the only value that opens the door to Approved, and everything else, including values you have never heard of, falls through to Quarantine. A check like "if the status is `THREATS_FOUND`, quarantine" would send a status AWS adds next year straight to Approved. D3 adds your own checks, and they can only demote a clean file, never promote a flagged one.

**The key is rebuilt, not read.** The event's `objectKey` gives you the `upload_id` and nothing else. The filename comes from the row, where B1 stored the cleaned name it used in the key. AWS's docs for this event don't say whether the key arrives percent-encoded the way S3's own notifications do, and rebuilding it means that never matters.

**Copy by version.** Without `VersionId` in `CopySource`, S3 copies whatever is current under that key. A client who uploads again after the scan could then get unscanned bytes into Approved. With it, you copy exactly what GuardDuty looked at, and step 10 deletes exactly that version. Move files with `copy_object`, never by downloading and uploading: the copy happens inside S3, with no file data passing through your function.

**The write order is copy, then update, then delete.** Think about what a crash leaves behind:

| Crash happens... | What is left | What the retry does |
|---|---|---|
| after the copy, before the update | the file in both buckets, the row still `PENDING` | copies again (same bytes, same key), updates, deletes: finished |
| after the update, before the delete | a finished row, and a leftover scanned version in Incoming | the update's condition fails, because the row is no longer `PENDING`. D4 turns that into "delete the leftover and stop" |

Putting the delete before the update would be worse. A crash between them leaves the row `PENDING` with its version gone, and the retry would see a missing version and mark a perfectly good file `STALE`. The row is written last among the changes that matter, and the delete, which can't be undone, is last of all.

**The conditional update.** `update_item` normally creates the row if it doesn't exist and overwrites it if it does. You don't want either. The update has three parts:

- `SET` the new status (`APPROVED` or `QUARANTINED`), `scanned_version_id` (the version you copied), and `destination_bucket`. For a quarantined file, also `SET` `reason`.
- `REMOVE expires_at`. Write those two words exactly. Lambda 1 gave the row a TTL timestamp so abandoned uploads clean themselves up; a finished upload must keep its row, so `GET /status` keeps answering for it.
- A `ConditionExpression` of `attribute_exists(upload_id) AND #s = :pending`. Write it exactly like that. The update succeeds only if the row exists and its status is still `PENDING`, so a replayed event changes nothing and a deleted row is never recreated.

`status` is a reserved word in DynamoDB expressions, so it can't be written bare. Put `{"#s": "status"}` in `ExpressionAttributeNames` and use `#s`. Put the values in `ExpressionAttributeValues`: `:pending` is `"PENDING"`, and the rest (`:new`, `:version`, `:destination`, `:reason`) are yours to name. Build the `SET` part as a string, adding the `reason` piece only when there is one, and put `REMOVE expires_at` at the end.

**Why one bug can only do so much.** The role you build in Part 3 can't create or delete rows: only `GetItem` and `UpdateItem`. Together with the condition, even a bug in this function can change a `PENDING` row exactly once, and nothing else.

**Docs:** [aws_sqs_queue](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/sqs_queue) · [Queue parameters](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-configure-queue-parameters.html) · [Encryption at rest](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-server-side-encryption.html)

The settings match C2's dead-letter queue, for the same reasons: `1209600` seconds is 14 days, the longest SQS allows, which gives you time to notice, fix, and replay; encryption keeps the records encrypted at rest. This is the second of the project's two failure queues. C's queue holds events EventBridge could not deliver to Lambda. This one holds events Lambda accepted and then failed to process. They catch different failures, and the project needs both.

Unlike C's queue, this one needs no queue policy. Lambda writes to it using your function's role, and you grant that in Part 3.

## Part 3: Data permissions (`modules/processing/iam.tf`, continued)

D1's role can write logs. Now it gets what the routing code needs, as a second document and a second inline policy, so the logging policy stays exactly as D1 left it. This is the permissions review that matters most in the project: every action below has a reason, and nothing else is allowed.

#### 3. What the role may do with data (permissions document)

**Block Type:** `data`
**Data Source Type:** `aws_iam_policy_document`
**Data Source Name:** `data_access`

Exactly six statements, nothing more. Every one has `effect` = `"Allow"`.

| `sid` | `actions` | `resources` | Why the router needs it |
|---|---|---|---|
| `"ReadIncoming"` | `["s3:GetObject", "s3:GetObjectVersion", "s3:GetObjectTagging", "s3:GetObjectVersionTagging"]` | a one-item list: the `incoming_bucket_arn` variable followed by `/*` | To copy a version, S3 checks that you may read it. `CopyObject` also copies the object's tags by default (its `TaggingDirective` setting defaults to `COPY`, and GuardDuty has just written its verdict as a tag), so you need to read them too. D3 reads the first bytes of the file. |
| `"ListIncoming"` | `["s3:ListBucket"]` | a one-item list: the `incoming_bucket_arn` variable itself, with no `/*` | Without it, S3 answers a request for a missing object with 403 (access denied) instead of 404 (not found), and D4 couldn't tell "the version is gone" from "I am not allowed". |
| `"DeleteScannedVersion"` | `["s3:DeleteObjectVersion"]` | a one-item list: the `incoming_bucket_arn` variable followed by `/*` | Deleting one specific version is a different action from `s3:DeleteObject`, which would only add a delete marker. |
| `"WriteDestinations"` | `["s3:PutObject", "s3:PutObjectTagging"]` | a two-item list: the `approved_bucket_arn` variable followed by `/*`, and the `quarantine_bucket_arn` variable followed by `/*` | Writing the copy, and the tags that come with it. The router never reads from either bucket. |
| `"UpdateRow"` | `["dynamodb:GetItem", "dynamodb:UpdateItem"]` | a one-item list holding the `table_arn` variable | Read the row, write the outcome. No `PutItem`, no `DeleteItem`. |
| `"ReportFailures"` | `["sqs:SendMessage"]` | a one-item list: the `arn` of `aws_sqs_queue.failures` | Lambda sends the failure record using the function's own role. |

Write it as six `statement` blocks.

**Docs:** [aws_iam_policy_document](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/data-sources/iam_policy_document) · [S3 actions and the permissions each API call needs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html) · [S3 resource ARNs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-arn-format.html)

**Docs:** [aws_lambda_function_event_invoke_config](https://registry.terraform.io/providers/hashicorp/aws/6.69.1/docs/resources/lambda_function_event_invoke_config) · [Asynchronous invocation, retries and destinations](https://docs.aws.amazon.com/lambda/latest/dg/invocation-async.html) · [depends_on](https://developer.hashicorp.com/terraform/language/meta-arguments/depends_on)

This resource sets how Lambda treats events it received asynchronously. By default it retries a failed event twice, waiting a minute and then two, and then discards it. Yours retries once and then writes a **failure record** to the queue: a JSON message with `requestPayload` (the original event, exactly as it arrived), `responsePayload` (the error), and `requestContext` (how many attempts, and why it gave up). The redrive script in Part 5 replays `requestPayload`.

- **`depends_on`** matters here. AWS's docs say the function's role needs `sqs:SendMessage` on the destination. Terraform only waits for resources you reference, and this resource references the function and the queue but not the role's policy. Without `depends_on`, the destination could exist before the permission that makes it work. The check matches this line as text, so write it exactly as `depends_on = [aws_iam_role_policy.router_data]`, on one line.
- **The destination is on failure only.** There is no `on_success`: a success leaves its trace in the table and in the logs, so a copy of every success would only add cost.

## Part 5: The redrive script (`scripts/redrive.sh`, new file)

When a failure has a cause you can fix (a permission, a bug), you want the failed events to go through again. `redrive.sh` does that: it takes each failure record out of the queue, sends the original event back to Lambda 2, and removes the record only after Lambda 2 succeeded.

#### 6. What the script must do

It needs the AWS CLI v2 and `jq` (`jq --version`; if it is missing, install it first: [download jq](https://jqlang.org/download/)). The script does this, in this order:

| Step | Behavior |
|---|---|
| 1 | Start with a shebang line (`#!/usr/bin/env bash`), then `set -euo pipefail` so the script stops at the first error. |
| 2 | Change into the repo root, so it works from any folder: `cd "$(dirname "$0")/.."`. |
| 3 | Read the queue URL and the function name from Terraform's outputs: `terraform output -raw router_failures_queue_url` and `terraform output -raw router_function_name`. (The first output exists after step 7.) |
| 4 | Make a temporary folder with `mktemp -d`, and remove it when the script exits (`trap`). |
| 5 | Loop: receive one message with `aws sqs receive-message --max-number-of-messages 1 --wait-time-seconds 5 --output json`, saved to a file in the temporary folder. An empty poll can leave that file empty or hold `{}`, so leave the loop unless `jq -e '.Messages \| length > 0'` succeeds on it. |
| 6 | The message body is a JSON string. With `jq`, take its `requestPayload` and write that, and only that, to a file in the temporary folder. |
| 7 | Invoke Lambda 2 with that file as the payload: `aws lambda invoke --function-name ... --payload fileb://... <response file> --query FunctionError --output text`. This is a normal (synchronous) invoke, so the answer tells you whether the function failed. |
| 8 | If the answer is anything but `None`, print a message and the response to standard error and `exit 1`, **without deleting the message**. It becomes visible in the queue again after its visibility timeout, so nothing is lost. |
| 9 | If it succeeded, delete the message with `aws sqs delete-message --receipt-handle ...`, and count it. |
| 10 | When the loop ends, print how many events were replayed, for example `Replayed 2 event(s).` |

Make it executable with `chmod +x scripts/redrive.sh` before you commit. Git records the executable bit when you `git add` the file. (On Windows, run `git update-index --chmod=+x scripts/redrive.sh` after adding it.)

**Why delete only after success.** SQS is at-least-once: a message you receive but don't delete comes back. That is exactly what you want here, because "replay failed again" must leave the record where you can find it. The cost is that a record can be replayed twice if the delete itself fails, which is why the router's conditional update from Part 1 makes a second run harmless.

**Why replay `requestPayload`.** The queue holds a record about the failure. The original event, the thing Lambda 2 expects, is inside it.

**Why this PR needs the lead's review.** Files under `scripts/` belong to the lead (see `CODEOWNERS`), like `milestones.txt`, so the lead's approval covers them. Point the lead to the script change when you mark the PR ready.

## Done when (in your own AWS account)

Run the commands one at a time. A command that runs over several lines (ending in `\`, or a `{ ... }` block) goes in whole. `apply` and `destroy` each stop and ask you to type `yes`, and `destroy` is finished when it prints `Destroy complete!`.

These commands need the AWS CLI v2 (`aws --version` should start with `aws-cli/2.`) and `jq`. Run everything in this section in one terminal window: the later commands use variables and functions the first ones define. This test is synthetic: it builds the scan-result event itself, so it doesn't wait on C's GuardDuty work. From the repo root:

```bash
terraform init -backend-config=backend.hcl
exec > >(tee ~/d2-done.txt) 2>&1
set -x
terraform apply
INCOMING=$(terraform output -raw incoming_bucket_name)
APPROVED=$(terraform output -raw approved_bucket_name)
QUARANTINE=$(terraform output -raw quarantine_bucket_name)
TABLE=$(terraform output -raw table_name)
ROUTER=$(terraform output -raw router_function_name)
ROLE=$(aws lambda get-function-configuration --function-name "$ROUTER" --query Role --output text); ROLE=${ROLE##*/}
QUEUE=$(terraform output -raw router_failures_queue_url)
T=$(mktemp -d)
printf '\x89PNG\r\n\x1a\n' > "$T/cat.png"
printf '\x89PNG\r\n\x1a\nnewer' > "$T/other.png"

# Helpers: seed a PENDING row plus an uploaded file, write a scan-result event for it, and show a row
new_upload() { # usage: new_upload <upload_id> <filename> <scan result status> <file to upload>
  aws dynamodb put-item --table-name "$TABLE" --item "{\"upload_id\": {\"S\": \"$1\"}, \"filename\": {\"S\": \"$2\"}, \"declared_type\": {\"S\": \"image/png\"}, \"status\": {\"S\": \"PENDING\"}, \"expires_at\": {\"N\": \"$(( $(date +%s) + 4500 ))\"}}"
  VERSION=$(aws s3api put-object --bucket "$INCOMING" --key "uploads/$1/$2" --body "$4" --query VersionId --output text)
  cat > "$T/event.json" <<EOF
{"detail-type": "GuardDuty Malware Protection Object Scan Result", "source": "aws.guardduty", "detail": {"scanStatus": "COMPLETED", "resourceType": "S3_OBJECT", "s3ObjectDetails": {"bucketName": "$INCOMING", "objectKey": "uploads/$1/$2", "versionId": "$VERSION", "s3Throttled": false}, "scanResultDetails": {"scanResultStatus": "$3", "threats": null, "statusReasons": null}}}
EOF
}
show() { # usage: show <upload_id>; prints: status, reason, destination bucket, expires_at
  aws dynamodb get-item --table-name "$TABLE" --key "{\"upload_id\": {\"S\": \"$1\"}}" \
    --query 'Item.[status.S, reason.S, destination_bucket.S, expires_at.N]' --output text
}

# 1. A clean file: expect Approved. The scanned version is gone, the row says APPROVED, and expires_at is removed.
#    A newer version is uploaded after the scan: the router must copy the scanned bytes, not the newer ones
ID=d2-$(date +%s)
new_upload "$ID" cat.png NO_THREATS_FOUND "$T/cat.png"
NEWER=$(aws s3api put-object --bucket "$INCOMING" --key "uploads/$ID/cat.png" --body "$T/other.png" --query VersionId --output text)
aws lambda invoke --function-name "$ROUTER" --payload "fileb://$T/event.json" "$T/out.json" --query '[StatusCode,FunctionError]' --output text
cat "$T/out.json"; echo
aws s3 cp "s3://$APPROVED/uploads/$ID/cat.png" - | cmp - "$T/cat.png" && echo "Approved holds the scanned bytes"
aws s3api list-object-versions --bucket "$INCOMING" --prefix "uploads/$ID/" --query 'Versions[].VersionId' --output text; echo "newer version: $NEWER"
show "$ID"

# 2. A malware verdict: expect Quarantine with the reason THREATS_FOUND
ID2=d2-bad-$(date +%s)
new_upload "$ID2" cat.png THREATS_FOUND "$T/cat.png"
aws lambda invoke --function-name "$ROUTER" --payload "fileb://$T/event.json" "$T/out.json" --query '[StatusCode,FunctionError]' --output text
aws s3api list-objects-v2 --bucket "$QUARANTINE" --prefix "uploads/$ID2/" --query 'Contents[].Key' --output text
show "$ID2"

# 3. A failure in the middle: block the row update, so the copy happens but nothing after it
ID3=d2-fail-$(date +%s)
new_upload "$ID3" cat.png NO_THREATS_FOUND "$T/cat.png"
aws iam put-role-policy --role-name "$ROLE" --policy-name deny-update --policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"dynamodb:UpdateItem","Resource":"*"}]}'
sleep 15
aws lambda invoke --function-name "$ROUTER" --invocation-type Event --payload "fileb://$T/event.json" "$T/out.json" --query StatusCode --output text
# Lambda retries once after about a minute, then writes the failure record (wait up to 5 minutes)
for i in $(seq 30); do
  N=$(aws sqs get-queue-attributes --queue-url "$QUEUE" --attribute-names ApproximateNumberOfMessages \
    --query Attributes.ApproximateNumberOfMessages --output text)
  [ "$N" != 0 ] && break
  sleep 10
done
echo "messages in router-failures: $N"
aws sqs receive-message --queue-url "$QUEUE" --visibility-timeout 0 --query 'Messages[0].Body' --output text \
  | jq '{condition: .requestContext.condition, error: .responsePayload.errorMessage, key: .requestPayload.detail.s3ObjectDetails.objectKey}'
aws s3api list-objects-v2 --bucket "$APPROVED" --prefix "uploads/$ID3/" --query 'Contents[].Key' --output text
aws s3api list-object-versions --bucket "$INCOMING" --prefix "uploads/$ID3/" --query 'Versions[].Key' --output text
show "$ID3"

# 4. Repair, then replay: expect "Replayed 1 event(s)." and a finished upload
aws iam delete-role-policy --role-name "$ROLE" --policy-name deny-update
sleep 15
scripts/redrive.sh
show "$ID3"
aws s3api list-object-versions --bucket "$INCOMING" --prefix "uploads/$ID3/" --query 'Versions[].Key' --output text

# Empty the buckets: Incoming is versioned, so remove every version and delete marker
aws s3 rm "s3://$APPROVED" --recursive
aws s3 rm "s3://$QUARANTINE" --recursive
aws s3api list-object-versions --bucket "$INCOMING" --output json \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' > "$T/versions.json"
[ "$(jq '.Objects | length' "$T/versions.json")" != 0 ] && aws s3api delete-objects --bucket "$INCOMING" --delete "file://$T/versions.json"
rm -r "$T"
terraform destroy
```

Expected:

1. `200 None`, then a response with `"destination"` set to your Approved bucket and `"reason": null`; `Approved holds the scanned bytes`; the Incoming list showing only the newer version (the same ID as the `newer version:` line, so the scanned version is gone and the newer one was never touched); and `APPROVED None <approved bucket> None` (status, no reason, destination, no `expires_at`). If the `cmp` line stays silent or prints a difference, your copy took the newer bytes: `CopySource` is missing its `VersionId`.
2. `200 None`; the key in Quarantine (listing works even though A3 blocks reading); `QUARANTINED THREATS_FOUND <quarantine bucket> None`.
3. `202` for the asynchronous invoke; `messages in router-failures: 1`; a JSON summary with `"condition": "RetriesExhausted"`, the error (an `AccessDeniedException` on `UpdateItem`), and the key; the file **in Approved**, the version **still in Incoming**, and the row still `PENDING` with an `expires_at` number. That is the write order working: the copy happened, the update failed, so nothing was deleted and the row never claimed success.
4. `Replayed 1 event(s).`, then `APPROVED ...` for the row, and `None` for the Incoming versions: the retry finished what the failure interrupted.

The cleanup block empties the three buckets before `terraform destroy`: Incoming is versioned, and `destroy` can't delete a bucket that still holds anything. The `deny-update` policy is not managed by Terraform, which is why step 4 removes it by hand.

Things that commonly go wrong:

- **`AccessDenied` in step 1 or 2**: the first thing to read is the function's log (`aws logs tail "/aws/lambda/$ROUTER" --since 10m`). The message names the action and the resource. Compare it with section 3's table; `s3:GetObjectVersionTagging` and `s3:PutObjectTagging` are the easy ones to forget.
- **`ConditionalCheckFailedException`**: the row wasn't `PENDING`. Each test needs its own new `ID`, and `new_upload` creates the row.
- **`ValidationException: Attribute name is a reserved keyword`**: you wrote `status` in an expression. Use the `#s` placeholder from section 1.
- **Step 3 prints `messages in router-failures: 0` after 5 minutes**: the deny may not have been active when the invoke ran, so the function succeeded. Run `show "$ID3"`: if it says `APPROVED`, repeat step 3 with a new ID and a longer `sleep`. Otherwise look at the `DestinationDeliveryFailures` metric for the function in CloudWatch: it counts records Lambda could not write to the queue, and a missing `sqs:SendMessage` is the usual cause.
- **`redrive.sh` prints `Replayed 0 event(s).`**: the queue was empty when the script looked. Queue counts can lag by a minute, so wait and run it again. (Step 3's peek used `--visibility-timeout 0`, so it did not hide the message.)
- **`redrive.sh: Permission denied`**: run `chmod +x scripts/redrive.sh`, and commit the change.
- **`apply` fails creating the destination config with an error about the destination**: run `terraform apply` again; if it persists, check that the queue's ARN reaches `destination` and that the role policy exists.
