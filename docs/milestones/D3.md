# D3: Your own checks: real type and real size

| | |
|---|---|
| **Portion** | D: Processing |
| **Branch** | `d3-validation` |
| **Depends on** | D2 (the routing) merged |
| **Files you touch** | `modules/processing/`: `src/handler.py`; `milestones.txt` |
| **Check** | Runs on GitHub on every push to `d3-validation`. The branch name decides which milestone is checked, so use this exact name. |

## Goal

GuardDuty answers one question: is this file malware? It doesn't answer two others, and both matter. Is the file what it claims to be? And is it as small as it claims? In this milestone Lambda 2 asks both itself, before it lets a clean file into Approved. You build:

- **A type check** that looks at the first bytes of the file, which no filename or request field can fake.
- **A size check** that asks S3 how big the scanned version really is.

A client can lie about both. B1 checks what the client says it is uploading, and B2's upload form limits the size, but those only guard the front door. Files can arrive other ways, and a renamed Windows executable is not malware to a scanner that finds no known virus in it. This is defense in depth, the Well-Architected idea of applying security at all layers: each layer assumes the one before it might have been bypassed.

There is no new Terraform in this milestone. The permissions D2 gave the role already cover both calls, and the environment variables (`ALLOWED_TYPES`, `MAX_SIZE_MB`) have been on the function since D1. You change only the handler.

**The rule that matters most.** These checks can only demote a file, never promote one. They run only when GuardDuty said `NO_THREATS_FOUND`. If GuardDuty flagged the file, it goes to Quarantine for GuardDuty's reason, and your checks never see it.

## Part 1: The type check (`modules/processing/src/handler.py`)

#### 1. Look at the first 16 bytes

Almost every file format starts with a few fixed bytes, called its **magic bytes** or signature. A PNG always starts with `89 50 4E 47`; a Windows executable always starts with `4D 5A` (the letters `MZ`). Renaming an `.exe` to `cat.png` changes the name and leaves those bytes alone, so reading them tells you what the file really is.

Add this to the handler:

| Step | Behavior |
|---|---|
| 1 | At the top of the file, read the `ALLOWED_TYPES` environment variable (a comma-separated string) and `split(",")` it into a list. |
| 2 | Write a small table of signatures, in plain Python (see below). |
| 3 | When the verdict is `NO_THREATS_FOUND`, read the first 16 bytes of the scanned version: `get_object` with `Bucket` = the Incoming bucket, the `Key`, the `VersionId`, and `Range="bytes=0-15"`. Read the body with `["Body"].read()`. |
| 4 | Find the signature the bytes start with (`bytes.startswith`), and take its MIME type. If none matches, the type is unknown (a value such as `None`). |
| 5 | If the detected type isn't in the allowed list, or is unknown, the file goes to Quarantine with the reason `INVALID_TYPE`. Otherwise it continues to Approved as before. |

The signatures to put in your table:

| MIME type | First bytes (hex) | As a Python bytes literal |
|---|---|---|
| `image/png` | `89 50 4E 47` | `b"\x89PNG"` |
| `image/jpeg` | `FF D8 FF` | `b"\xff\xd8\xff"` |
| `application/pdf` | `25 50 44 46` | `b"%PDF"` |
| `application/zip` | `50 4B 03 04` | `b"PK\x03\x04"` |

Write the literals exactly like that; the check looks for them. ZIP is in the table even though the default allowed list doesn't include it: the table says what a file *is*, and `ALLOWED_TYPES` says what the project *accepts*. Someone who adds `application/zip` to the list in `terraform.tfvars` gets it working with no code change.

**Compare with the allowed list, not with what the client declared.** The row has a `declared_type`, and you must not use it here. The point of the check is that the client's word isn't evidence. A file whose real type is allowed passes, whatever it said it was.

**Why a ranged read.** `Range="bytes=0-15"` makes S3 send 16 bytes instead of the whole file, which could be many megabytes. It is the cheapest check there is, and there's no reason to pull more. It also keeps this function small and fast, which D4 will measure.

**Why not a library.** Python has a package called `python-magic` that does this, but it depends on an operating-system library the Lambda runtime doesn't have. A short table of the formats you accept is also easier to review: every type the project accepts is written down in one place.

**What this check cannot do.** It proves the file *starts* like a PNG. It doesn't prove the rest is a valid image, and it isn't a malware scan. That is GuardDuty's job, and the reason both layers exist.

## Part 2: The size check (`modules/processing/src/handler.py`, continued)

#### 2. Ask S3 how big the file is

B2's upload form already refuses a file over `MAX_SIZE_MB`. This check is the second layer: it measures the scanned version itself, so a file that got into Incoming some other way is still caught.

| Step | Behavior |
|---|---|
| 1 | At the top of the file, read `MAX_SIZE_MB` from the environment and turn it into a number of bytes: `int(os.environ["MAX_SIZE_MB"]) * 1024 * 1024`. Write the multiplication exactly like that (the check looks for it). |
| 2 | When the verdict is `NO_THREATS_FOUND`, **before** the type check, call `head_object` with the Incoming bucket, the `Key`, and the `VersionId`. It returns the version's metadata without its content. |
| 3 | Read the size from the response's `ContentLength`. If it is more than the limit, the file goes to Quarantine with the reason `TOO_LARGE`, and you skip the type check. |

**Why before the type check.** It is cheaper (no body is read), and it means a file that is both too big and the wrong type is reported as `TOO_LARGE`. Pick one order and keep it; the reason a person sees should not change from run to run.

**Why `head_object` and not the row's `declared_size`.** The row records what the client *said* when it asked for an upload URL. `ContentLength` is what S3 is actually holding. The check exists for the case where those two differ.

**Why the version.** Pass the `VersionId` here as well. Without it, S3 would describe whatever version is current, which is not necessarily the one GuardDuty scanned.

**The reasons are now complete.** With D3, Lambda 2 can write every `reason` in the project's data contract: `THREATS_FOUND`, `UNSUPPORTED`, `ACCESS_DENIED`, and `FAILED` (copied from GuardDuty's verdict), `INVALID_TYPE` and `TOO_LARGE` (yours), and `STALE`, which D4 adds.

## Check it

### How to see your results

The check never runs on your machine. It runs on GitHub every time you push, and the results are stored there: on the run's page under **Actions**, and on your pull request as the **ci** check. There are two ways to see them.

**After a push (automatic):** open the repo on GitHub, click **Actions**, click the newest run, and scroll to **Summary**. The table lists every step with ✅ or ❌. Click **Output of the failed steps** under it to see what each ❌ expected and what it found.

**From your terminal (re-check without pushing):**

```bash
scripts/remote-check.sh
```

This asks GitHub to run the check again on your branch, waits for it to finish, and prints your progress. When the milestone is complete, it looks like this:

```

Waiting for GitHub to start the run...
Run finished in 71s

D3 progress: 2 of 2 steps done
  ✅ formatting, init, validate
  ✅ step 1 (types)
  ✅ step 2 (size)
  ✅ earlier milestones still pass (M0, A1, A2, D1, D2)

👍 D3 passed. Next: run "Done when" in your own AWS account.

Full results: https://github.com/umbra-codex/aws-secure-file-upload/actions/runs/123456789
```

The list of earlier milestones is whatever `milestones.txt` holds on your branch, so yours may differ from this example. If any line shows ❌, the first one is marked `<- next`, and the last line names the step to fix. It checks what you have **pushed**, not unsaved edits; if you have uncommitted changes or unpushed commits, it says so first. Nothing is saved on your machine: close the terminal and the results are still on GitHub. It needs the GitHub CLI, signed in (`gh auth login`). If the script itself fails, open the newest run under **Actions** instead; the same table is in its Summary.

**To re-check after a fix:** format, commit, and push. The push runs the check automatically. Run `scripts/remote-check.sh` only when you want a fresh run without pushing anything new.

D3 runs in two steps:

| Step | File | Checks |
|---|---|---|
| 1 (types) | src/handler.py | the file reads `ALLOWED_TYPES`, reads 16 bytes of the scanned version, knows all four signatures, and uses `INVALID_TYPE` |
| 2 (size) | src/handler.py | the file reads `MAX_SIZE_MB`, measures the real size with `head_object`, and uses `TOO_LARGE` |

Every milestone already listed in `milestones.txt` is re-checked too. If the summary shows only `formatting`, `init`, and `validate` with no step rows, `validate` failed and the run stopped before any step ran: read the `validate` output. If `formatting` is ❌, run `terraform fmt -recursive`, commit, and push. See A1's [Check it](A1.md#check-it) for how to read each kind of failure.

The check reads your file; it can't tell whether the checks run in the right order, whether they run only for clean files, or whether the reasons end up in the right place. "Done when" tests all of that against real S3.

## Done when (in your own AWS account)

These commands need the AWS CLI v2 (`aws --version` should start with `aws-cli/2.`) and `jq`. Run everything in this section in one terminal window: the later commands use variables and functions the first ones define. The test is synthetic, like D2's. From the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
INCOMING=$(terraform output -raw incoming_bucket_name)
APPROVED=$(terraform output -raw approved_bucket_name)
QUARANTINE=$(terraform output -raw quarantine_bucket_name)
TABLE=$(terraform output -raw table_name)
ROUTER=$(terraform output -raw router_function_name)
MAX=$(echo var.max_size_mb | terraform console)
T=$(mktemp -d)
printf '\x89PNG\r\n\x1a\n' > "$T/real.png"                      # a real PNG signature
printf 'MZ\x90\x00\x03\x00\x00\x00' > "$T/fake.png"              # a Windows executable's first bytes
{ printf '\x89PNG\r\n\x1a\n'; head -c $(( (MAX + 1) * 1024 * 1024 )) /dev/zero; } > "$T/big.png"   # a PNG one MB over the limit

# Helpers: seed a PENDING row plus an uploaded file, write a scan-result event for it, and show a row
new_upload() { # usage: new_upload <upload_id> <filename> <scan result status> <file to upload>
  aws dynamodb put-item --table-name "$TABLE" --item "{\"upload_id\": {\"S\": \"$1\"}, \"filename\": {\"S\": \"$2\"}, \"declared_type\": {\"S\": \"image/png\"}, \"status\": {\"S\": \"PENDING\"}, \"expires_at\": {\"N\": \"$(( $(date +%s) + 4500 ))\"}}"
  VERSION=$(aws s3api put-object --bucket "$INCOMING" --key "uploads/$1/$2" --body "$4" --query VersionId --output text)
  cat > "$T/event.json" <<EOF
{"detail-type": "GuardDuty Malware Protection Object Scan Result", "source": "aws.guardduty", "detail": {"scanStatus": "COMPLETED", "resourceType": "S3_OBJECT", "s3ObjectDetails": {"bucketName": "$INCOMING", "objectKey": "uploads/$1/$2", "versionId": "$VERSION", "s3Throttled": false}, "scanResultDetails": {"scanResultStatus": "$3", "threats": null, "statusReasons": null}}}
EOF
}
show() { # usage: show <upload_id>; prints: status, reason, destination bucket, expires_at
  aws dynamodb get-item --table-name "$TABLE" --key "{\"upload_id\": {\"S\": \"$1\"}}" \
    --query 'Item.[status.S, reason.S, destination_bucket.S, expires_at.N]' --output text
}
route() { # usage: route <name> <file> <verdict>; runs the whole test for one upload and prints the row
  local id="d3-$1-$(date +%s)"
  new_upload "$id" cat.png "$3" "$2"
  aws lambda invoke --function-name "$ROUTER" --payload "fileb://$T/event.json" "$T/out.json" --query '[StatusCode,FunctionError]' --output text
  show "$id"
}

# 1. A real PNG: expect APPROVED
route real "$T/real.png" NO_THREATS_FOUND
# 2. An executable named cat.png: expect QUARANTINED, INVALID_TYPE
route fake "$T/fake.png" NO_THREATS_FOUND
# 3. A real PNG over the size limit, put straight into Incoming: expect QUARANTINED, TOO_LARGE
route big "$T/big.png" NO_THREATS_FOUND
# 4. An executable GuardDuty flagged: expect THREATS_FOUND, not INVALID_TYPE (your checks never run)
route flagged "$T/fake.png" THREATS_FOUND

# Empty the buckets: Incoming is versioned, so remove every version and delete marker
aws s3 rm "s3://$APPROVED" --recursive
aws s3 rm "s3://$QUARANTINE" --recursive
aws s3api list-object-versions --bucket "$INCOMING" --output json \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' > "$T/versions.json"
[ "$(jq '.Objects | length' "$T/versions.json")" != 0 ] && aws s3api delete-objects --bucket "$INCOMING" --delete "file://$T/versions.json"
rm -r "$T"
terraform destroy
```

Expected, one `200 None` line and one row line per test:

1. `APPROVED None <approved bucket> None`
2. `QUARANTINED INVALID_TYPE <quarantine bucket> None`
3. `QUARANTINED TOO_LARGE <quarantine bucket> None`
4. `QUARANTINED THREATS_FOUND <quarantine bucket> None`

`echo var.max_size_mb | terraform console` asks Terraform for the limit you actually deployed with, so the oversized file is always one megabyte over it. The upload in test 3 goes straight to S3 with your own credentials, which is exactly the kind of path the second layer exists for: B2's form would have refused it. The cleanup block empties the three buckets before `terraform destroy`, because Incoming is versioned.

Things that commonly go wrong:

- **Test 1 lands in Quarantine with `INVALID_TYPE`**: the signature table or the comparison is wrong. `aws logs tail "/aws/lambda/$ROUTER" --since 10m` shows the log line; print the 16 bytes your code read (temporarily) to see what it compared. A PNG file starts `89 50 4E 47`; if you wrote it as text (`"\x89PNG"` without the `b`), it is a string, not bytes.
- **Test 3 comes back `APPROVED`**: the size check isn't running, or it compares megabytes with bytes. `MAX_SIZE_MB` is a string; the multiplication needs `int()`.
- **Test 4 says `INVALID_TYPE`**: your checks run for every verdict. They must run only when GuardDuty said `NO_THREATS_FOUND`.
- **`AccessDenied` on `head_object`**: HEAD needs `s3:GetObject`, which `ReadIncoming` grants on `incoming/*`. Check D2's resource ends in `/*`.
- **`terraform console` prints nothing**: run `terraform init -backend-config=backend.hcl` first, in the repo root.
- **`The specified key does not exist` from `get_object`**: the key you rebuilt doesn't match the one in Incoming. It must be `uploads/{upload_id}/` followed by the row's `filename`.
