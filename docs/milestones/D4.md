## Goal

Lambda 2 works on a clean path. Real traffic isn't one. Lambda can deliver the same event twice, even when nothing failed (AWS says so in its docs). A person can upload a file through the console, with no row behind it. A scanned version can disappear before the router gets to it. In this milestone you make the router **idempotent**: running it twice on the same event leaves the same result as running it once. You build:

- **Four edge cases** in the handler: no row, a row that is no longer `PENDING`, a version that is gone, and a replayed update.
- **A right-sized function.** You measure what the function really uses, and lower the memory you started with in D1.

Two ideas to hold on to:

- **At-least-once delivery.** Lambda's asynchronous queue promises that an event arrives at least once, not exactly once. Any function behind such a queue has to survive a repeat. The conditional update from D2 already makes the *row* safe; this milestone makes the *whole function* safe.
- **Expected failures aren't errors.** An error makes Lambda retry and then land the event in the failure queue, where a person has to deal with it. That is right for a bug and wrong for a harmless case such as "this upload has no row". Each case below says which kind it is.

## Part 1: The edge cases (`modules/processing/src/handler.py`)

#### 1. What the handler must also do

Everything from D2 and D3 stays. These are the changes, in the order they happen in the function:

| Step | Situation | Behavior |
|---|---|---|
| 1 | **No row.** `get_item` returns no `Item` (use `.get("Item")`). Also treat an object key with no upload ID in it as no row: split the key on `/` and take the second part only if there is one and it isn't empty (a console "folder" object named `uploads/` has an empty one). | Log a warning with the `upload_id` (`logger.warning`), and return a dictionary such as `{"result": "no_row"}`. Don't raise. This is a console upload or a leftover object, and retrying can never create the missing row. |
| 2 | **The row is no longer `PENDING`.** The upload already has an outcome. | Log it, delete the scanned version from Incoming (it is a leftover), and return `{"result": "already_processed"}`. Don't copy, don't update. Do this before any copy. |
| 3 | **The scanned version is gone.** `head_object`, `get_object`, or `copy_object` fails with a `ClientError` whose code is `NoSuchKey`, `NoSuchVersion`, or `404`. | Log a warning with the `upload_id` and `version_id`. Record the upload as `QUARANTINED` with the reason `STALE`, with no `destination_bucket` (nothing was copied), and return success. Don't retry it: the bytes will not come back. Any other `ClientError` code is a real problem: `raise` it. |
| 4 | **The update's condition fails** (`ConditionalCheckFailedException`). Another run finished this upload while this one was working. | Log it at info level and carry on to delete the scanned version. It is not an error. Any other `ClientError` code: `raise`. |

Read the error code from the exception: `err.response["Error"]["Code"]`, where `err` is the `ClientError` you caught (`from botocore.exceptions import ClientError`). A request that uses `HEAD` has no response body, so boto3 reports a missing object as the plain code `404`; that's why `404` is in the list.

**The final update for `STALE`.** It is the same conditional update as before: set the status to `QUARANTINED`, `reason` to `STALE`, and `scanned_version_id`; remove `expires_at`; no `destination_bucket`. After it, delete the (already missing) version. S3 normally answers success when you delete a version that is already gone. If your run raises instead, the log names the error code; handle it the way step 3 does.

**What the reasons mean now.** `STALE` means "GuardDuty scanned a version that no longer exists when the router came for it". It can happen if a lifecycle rule or a person removed the file first. The uploader sees `QUARANTINED` with that reason and uploads again.

**What stays an error, on purpose.** `AccessDenied` from S3 or DynamoDB, a throttling error, or a timeout all `raise`. Those are real problems or transient ones, and the retry plus the failure queue is exactly the machinery for them. If you catch *everything*, you hide the very failures the queue exists to show you. That is why step 3 and step 4 look at the code and re-raise the rest.

**The mechanics, in plain terms.** You are adding `if` and `try`/`except` around code you already have. Keep each case small and keep the happy path readable: a reviewer should be able to find the four cases above in the file without searching.

## Part 2: Memory (`modules/processing/lambda.tf`)

You set `memory_size` to 512 in D1 because you had no numbers yet. Now you can measure what the function really needs.

#### 2. Measure, then choose

Lambda charges for memory multiplied by time, and gives a function CPU in proportion to its memory. Lambda 2 spends nearly all of its time waiting for S3 and DynamoDB, which doesn't go faster with more CPU. So extra memory is mostly money spent on nothing.

Collect the numbers before you edit anything. Run the "Done when" commands below once with the function still at 512 (stop after the measuring line, don't destroy yet). Every invocation writes a **report** line to the log. With JSON logging on, it is a JSON object like this (from AWS's schema):

```json
{"time": "2026-10-21T14:03:11.402Z", "type": "platform.report", "record": {"metrics": {"durationMs": 693.92, "billedDurationMs": 694, "initDurationMs": 397.68, "maxMemoryUsedMB": 84, "memorySizeMB": 512}, "requestId": "6d68ca91-..."}}
```

`maxMemoryUsedMB` is the most memory the function touched during that invocation, and `durationMs` is how long it ran. (`initDurationMs` appears only on a cold start.) Take the **largest** `maxMemoryUsedMB` across your runs, then set `memory_size` in `lambda.tf` to the smallest of these four values that is **at least twice that number**:

| Allowed values | `128`, `192`, `256`, `384` |
|---|---|

Twice is the headroom for a larger event or a slower library import. The check accepts any of the four, because it can't see your logs; your reviewer compares your choice with the numbers you paste into the PR. Leave `timeout` at 30.

After the change, run the tests again (the second block in "Done when"). The `durationMs` values will usually be a little higher, because there's less CPU. If a typical invocation is more than about twice as slow as before, you have chosen too low.

| Argument | Set To |
|---|---|
| `memory_size` | your number, one of `128`, `192`, `256`, `384` |

## Done when (in your own AWS account)

These commands need the AWS CLI v2 (`aws --version` should start with `aws-cli/2.`) and `jq`. Run everything in this section in one terminal window: the later commands use variables and functions the first ones define. The test is synthetic. It has three blocks: the setup and tests (block 1), a second run after you change the memory (block 2), and the cleanup (block 3). From the repo root:

```bash
terraform init -backend-config=backend.hcl
terraform apply
INCOMING=$(terraform output -raw incoming_bucket_name)
APPROVED=$(terraform output -raw approved_bucket_name)
QUARANTINE=$(terraform output -raw quarantine_bucket_name)
TABLE=$(terraform output -raw table_name)
ROUTER=$(terraform output -raw router_function_name)
T=$(mktemp -d)
printf '\x89PNG\r\n\x1a\n' > "$T/cat.png"
printf '\x89PNG\r\n\x1a\nreplacement' > "$T/other.png"

# Helpers: seed a PENDING row plus an uploaded file, write a scan-result event for it, and show a row
new_upload() { # usage: new_upload <upload_id> <filename> <scan result status> <file to upload>
  aws dynamodb put-item --table-name "$TABLE" --item "{\"upload_id\": {\"S\": \"$1\"}, \"filename\": {\"S\": \"$2\"}, \"declared_type\": {\"S\": \"image/png\"}, \"status\": {\"S\": \"PENDING\"}, \"expires_at\": {\"N\": \"$(( $(date +%s) + 4500 ))\"}}"
  VERSION=$(aws s3api put-object --bucket "$INCOMING" --key "uploads/$1/$2" --body "$4" --query VersionId --output text)
  cat > "$T/event.json" <<EOF
{"detail-type": "GuardDuty Malware Protection Object Scan Result", "source": "aws.guardduty", "detail": {"scanStatus": "COMPLETED", "resourceType": "S3_OBJECT", "s3ObjectDetails": {"bucketName": "$INCOMING", "objectKey": "uploads/$1/$2", "versionId": "$VERSION", "s3Throttled": false}, "scanResultDetails": {"scanResultStatus": "$3", "threats": null, "statusReasons": null}}}
EOF
}
show() { # usage: show <upload_id>; prints: status, reason, destination bucket, expires_at
  aws dynamodb get-item --table-name "$TABLE" --key "{\"upload_id\": {\"S\": \"$1\"}}" \
    --query 'Item.[status.S, reason.S, destination_bucket.S, expires_at.N]' --output text
}
invoke() { # usage: invoke; sends $T/event.json to the router and prints the status, any FunctionError, and the result
  aws lambda invoke --function-name "$ROUTER" --payload "fileb://$T/event.json" "$T/out.json" --query '[StatusCode,FunctionError]' --output text
  cat "$T/out.json"; echo
}
run_tests() {
  local id id3 id4 etag
  # 1. A repeat: run the same event twice. The second run says already_processed and changes nothing
  id=d4-dup-$(date +%s)
  new_upload "$id" cat.png NO_THREATS_FOUND "$T/cat.png"
  invoke; show "$id"
  etag=$(aws s3api head-object --bucket "$APPROVED" --key "uploads/$id/cat.png" --query ETag --output text)
  invoke; show "$id"
  echo "Approved object unchanged: $([ "$etag" = "$(aws s3api head-object --bucket "$APPROVED" --key "uploads/$id/cat.png" --query ETag --output text)" ] && echo yes || echo NO)"

  # 2. A leftover version: a second scanned version of a finished upload is deleted, and Approved is not overwritten
  VERSION=$(aws s3api put-object --bucket "$INCOMING" --key "uploads/$id/cat.png" --body "$T/other.png" --query VersionId --output text)
  sed -i.bak "s/\"versionId\": \"[^\"]*\"/\"versionId\": \"$VERSION\"/" "$T/event.json"
  invoke
  aws s3api list-object-versions --bucket "$INCOMING" --prefix "uploads/$id/" --query 'Versions[].VersionId' --output text
  echo "Approved object unchanged: $([ "$etag" = "$(aws s3api head-object --bucket "$APPROVED" --key "uploads/$id/cat.png" --query ETag --output text)" ] && echo yes || echo NO)"

  # 3. No row: an event for an upload that was never requested. Success, no FunctionError
  id3=d4-norow-$(date +%s)
  new_upload "$id3" cat.png NO_THREATS_FOUND "$T/cat.png"
  aws dynamodb delete-item --table-name "$TABLE" --key "{\"upload_id\": {\"S\": \"$id3\"}}"
  invoke

  # 4. A vanished version: delete the scanned version before the router runs. Expect QUARANTINED, STALE
  id4=d4-stale-$(date +%s)
  new_upload "$id4" cat.png NO_THREATS_FOUND "$T/cat.png"
  aws s3api delete-object --bucket "$INCOMING" --key "uploads/$id4/cat.png" --version-id "$VERSION"
  invoke; show "$id4"
}
report() { # the largest memory use and the durations from the log
  aws logs tail "/aws/lambda/$ROUTER" --since 30m | grep platform.report | sed 's/^[^{]*//' \
    | jq -c '.record.metrics | {durationMs, maxMemoryUsedMB, memorySizeMB}'
}

# Block 1: run the tests with the function as it is now, then read the numbers
run_tests
sleep 20
report
```

Expected from `run_tests` (one `200 None` line plus the result for each `invoke`):

1. First run: `APPROVED None <approved bucket> None`. Second run: `{"result": "already_processed"}`, the same row, and `Approved object unchanged: yes`.
2. `{"result": "already_processed"}`, then `None` for the Incoming versions (the leftover is deleted), and `Approved object unchanged: yes`.
3. `200 None` and `{"result": "no_row"}`. A warning in the log, no failure record, no error.
4. `QUARANTINED STALE None None`.

The `report` lines show `durationMs`, `maxMemoryUsedMB`, and `memorySizeMB` for each invocation. Use the largest `maxMemoryUsedMB` to choose `memory_size` (section 2), save `lambda.tf`, and run block 2. Paste both reports into your PR.

```bash
# Block 2: after changing memory_size in lambda.tf
terraform apply
run_tests
sleep 20
report
```

Expected: the same results as block 1. The second `report` prints block 1's lines again (the log keeps them) followed by the new ones, and only the later lines show `memorySizeMB` at your new value.

```bash
# Block 3: cleanup
# Empty the buckets: Incoming is versioned, so remove every version and delete marker
aws s3 rm "s3://$APPROVED" --recursive
aws s3 rm "s3://$QUARANTINE" --recursive
aws s3api list-object-versions --bucket "$INCOMING" --output json \
  --query '{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}' > "$T/versions.json"
[ "$(jq '.Objects | length' "$T/versions.json")" != 0 ] && aws s3api delete-objects --bucket "$INCOMING" --delete "file://$T/versions.json"
rm -r "$T"
terraform destroy
```

Things that commonly go wrong:

- **Test 1's second run raises `ConditionalCheckFailedException`**: the "not `PENDING`" check from section 1 is missing or runs after the update. It must run right after reading the row, before any copy.
- **Test 2 shows `NO` for "unchanged"**: the replay copied the leftover over the approved file. The "not `PENDING`" case must delete and stop, never copy.
- **Test 3 prints a `FunctionError`**: the handler raised on the missing row. Read the response (`cat "$T/out.json"`) for the line, and check you use `.get("Item")`, not `["Item"]`.
- **Test 4 raises `AccessDenied` or another code**: the router can't tell "gone" from "not allowed" without `s3:ListBucket` (D2's `ListIncoming` statement), and your code re-raises codes it doesn't expect. If you see a 404-class code that isn't in the list, the log line names it: add it. If you see a 403, check `ListIncoming`.
- **Test 1's second run raises an error about the delete**: the replay deleted a version that was already gone, and S3 didn't treat that as success. Read the code in the log and catch it in your delete step, the same way as in step 3.
- **`report` prints nothing**: the report lines take a few seconds to arrive. Wait and run `report` again. If it still prints nothing, run `aws logs tail "/aws/lambda/$ROUTER" --since 30m | grep -i report` to see how the line is formatted.
- **`jq: parse error` in `report`**: a line that matched isn't pure JSON. Use `grep '"type": "platform.report"'` instead of `grep platform.report`.
- **The numbers look odd after a cold start**: the first invocation after a deploy includes `initDurationMs` and uses the most memory. That's the number to size against, not the average.
